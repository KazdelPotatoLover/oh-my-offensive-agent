# 上下文压缩与停止误报修复

日期：2026-10-23。实现基线：`9d1d027`。本文记录本地修复；运行中的容器需重新构建后加载。

## 失败原因

最近两个真实 Run（`7e9320a9`、`b7bceb67`）最终显示 `provider_error`，但其中多次 Planner 会话的直接原因是本地 `context_compaction_failed`。

旧压缩器无条件保留最后 8 条消息。真实失败会话恰好只有 7～8 条消息，虽然已经包含完整的 assistant 工具调用及对应结果，算法仍找不到允许压缩的位置。与此同时，每轮 Planner 把探索图、观察原文等拼入初始输入，初始 user 消息约 64～69 KB；加上工具输出、原生推理状态和 JSON 编码后超过默认 98,304 字节窗口。

这个窗口是本项目的本地上下文保护值，不是模型调用次数预算，也不是供应商宣称的 token 容量。单纯追加次数不能修复这个错误。Engine 又把未分类的错误归入 `provider_error`，掩盖了真正原因。

现场另有真实的供应商 503/临时传输错误；这部分仍由已有的有界重试处理，不能与本地压缩错误混为一谈。

## 修复行为

1. 按完整协议边界逐步缩短历史，取消固定 8 条的限制。始终保留 system、最初的用户请求和最近一组完整交换，不拆开多工具批次；保留下来的原生 Responses/reasoning 数据不改写。
2. 历史索引保留最近的摘要、调用 ID 和引用，明确不是新证据。原始消息仍完整保存在数据库，新检查点策略记为 `extractive_protocol_blocks_v2`；旧检查点继续兼容读取，来源哈希和 Epoch 校验保留。
3. Planner/Worker 预载探索图按上下文窗口分配空间，默认上限 16 KiB。过大时缩成合法 JSON 摘要，保留 ID、状态、近期成果与发现的验证状态，并标明截短及各节条数。API 的原始探索图和证据不变。
4. Planner 观察预载使用最近 20 条的摘录，工作项/资产列表限制预载条数；跨轮待办提前放置，避免被观察原文挤掉。完整信息仍按图节点、产物和 Worker trace 查询。
5. 无法安全压缩的受保护输入返回类型化 `ErrContextLimit`。Planner 会话停止原因是 `context_limit_exceeded`，Run 以 `stopped / needs_input` 结束并保存中文诊断，不再伪装成供应商故障。Worker 的同类错误保留局部原因，交给 Planner 判断，不自动重放工具。
6. 保存检查点时的数据库故障归入持久化故障；执行已经取消时保留取消原因。
7. Worker 装配阶段若上下文已取消，沿用真实取消原因，避免把它误报为 `profile_load_failed` 等能力错误。真正的配置读取错误记录带 Run/WorkItem/Session ID 的服务日志；授权和版本校验继续生效。

现场 `profile_load_failed` 与 Planner 收尾时间相邻，可能是父执行取消引起的连带现象；已有记录没有保存底层错误，不能据此断言能力配置丢失。本次修复消除这条错误归因路径，没有改写旧失败记录。

## 与 ARTEX 的关系

参考相邻 ARTEX 的 `agent/planner.go`、`agent/worker.go`、`agent/provider.go:compactionConfig`：Planner 每轮新会话并读取当前态势；Worker 保持稳定对话；上下文压缩交给 agent-core SDK。任务边界与动态态势分开考虑。

本工程继续使用 PostgreSQL transcript/checkpoint 和现有 Provider，因此完整协议块抽取、字节窗口及错误分类属于本地适配，不是声称复制了 SDK 内部压缩实现。没有用增加总预算、自动重跑外部动作或改写失败历史替代修复。

## 使用

在仓库根目录运行原有脚本，重建服务即可，无新增迁移和环境变量：

```bash
./scripts/start-local.sh
```

历史 failed 记录保持原样。重启不会自动恢复旧任务；恢复/新执行才会运行修复后的代码。同一份确实超过保护窗口的任务输入不能靠反复重试解决，且已有 Run 的冻结配置不会因修改默认值而自动变化。
