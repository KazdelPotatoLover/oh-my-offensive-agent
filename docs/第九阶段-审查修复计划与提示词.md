# 第九阶段审查修复计划与编码提示词

日期：2026-10-21。本文是修复计划，尚未实施。

当前第九阶段已有审核事务、历史查询、当前报告和前端表单，尚未提交。上一轮检查确认后端编译、go vet、前端生产构建通过；未重新运行数据库集成测试或浏览器验收。验收文档中的既有 PASS 是原实现者记录，不等于本轮复验结果。

## 修复目标

保住审核历史、正确区分输入错误与服务故障，并用真实的事务中途失败证明原子性。完成这三项后再做整体验收，无需改造 Engine。

## 1. 防止删除任务时抹掉审核历史

### 原因

`014_finding_reviews.up.sql` 中两个外键都使用 `ON DELETE CASCADE`；现有删除任务接口最终执行物理删除，任务关联 Run、Finding 也会级联删除，因此人工审核历史会一起消失。

### 处理方案

本阶段采用明确的保留策略：**存在审核历史的任务禁止物理删除，返回 409；无审核历史且无活动 Run 的任务仍按现有规则删除。** 页面提示保留原因。不引入软删除或归档系统。

1. 将 `finding_reviews.finding_id` 与 `finding_reviews.run_id` 外键改为限制父记录删除，使用具名的 `ON DELETE RESTRICT` 外键。数据库约束承担最终保护，不能仅靠应用层先查再删。
2. 删除任务服务可预先检测是否有审核记录，给出可理解的业务错误，例如 `ErrTaskHasReviewHistory`。同时识别删除语句返回的审核外键冲突并映射到同一错误，防止检查与删除间发生新审核时漏掉保护；不要把所有外键冲突都误归类。
3. Handler 把该业务错误映射到 409，前端删除入口显示“该任务包含人工审核历史，暂不支持删除”。检查现有前端是否已经展示 API 错误，优先复用。
4. 现有活动 Run 不允许删除、未知任务返回 404 的行为保留。不得通过先删审核历史再删任务绕过限制。

### 迁移策略

本轮只读检查发现开发库为迁移 013，但其他环境可能已经使用 014。编码 Agent 必须先确认实际环境，不能仅凭迁移文件尚未提交推断它从未执行。

为同时支持新库和已执行 014 的库，优先新增 015 迁移替换上述外键，不依赖修改旧文件生效。新库按 014 → 015 建立最终约束。不要回滚或重置已有审核库；015 降级应明确拒绝恢复会删除审计历史的级联语义，说明这一保留策略。

集成测试里原有 `TRUNCATE ... CASCADE` 仅用于独立测试库清理；这是测试管理操作，不是产品删除入口。不要把它误用到开发库或当作审核保留策略的实现。

### 验收

- 已结束任务产生审核后，调用删除 API 返回 409；任务、Run、Finding、历史均保留。
- 直接尝试删除其 Finding 或 Run，被外键拒绝，审核历史仍在。
- 没有审核历史且没有活动 Run 的任务仍可正常删除。
- 并发审核与删除不能产生“审核成功提交，历史随后被删除”的结果；一方可失败，但已提交的审核历史必须保留。用同步屏障/锁组织测试，不依赖固定 sleep。
- 在独立库验证从 013 新建及从已有审核数据的 014 升到 015，两种路径均保留内容与版本。

## 2. 输入错误返回 400

### 原因

`ReviewFinding` 对审核人超过 100、说明超过 2000 的情况返回普通 `errors.New`，Handler 只识别部分已知错误，因此把这些输入问题当作 500。

### 处理方案

1. 新增可通过 `errors.Is` 判断的输入错误，或统一使用项目现有类型化校验错误；长度超限、负 expected_version 都归为 400。
2. 明确长度单位。建议按 trim 后的 Unicode 字符数限制审核人 100、说明 2000，使用 `utf8.RuneCountInString`，避免中文因字节数提前超限；前后端提示一致。
3. 为审核 POST 设置请求体上限，例如 32 KiB。超过上限返回 413；非法 JSON 返回 400。处理读取超限错误时不能统一改成 400。
4. 数据库异常仍为 500；不要把所有错误都映射成 400，响应不要透出数据库内部错误。
5. 同幂等键的内容比较补上原始 expected_version：它应等于已有记录的 from_version。同键仅改版本也属于不同请求，应返回 409；原请求即使版本已过期仍可幂等重放。

### 验收

覆盖 trim 后字符数刚好达到上限及超过上限、中英文输入、空值、负版本、缺失版本、超大请求体和非法 JSON。每个被拒绝的请求都不新增历史、不增加版本。保留原有幂等重放测试，并增加“同键仅改 expected_version”用例。

## 3. 验证事务中途失败确实回滚

### 原因

现有 `TestPhase9_TransactionRollbackOnFailure` 在调用服务前就取消 context，通常连事务都未开始。它只能证明“未执行时不写入”，不能证明“历史已插入后，Finding 更新失败会回滚”。

### 处理方案

1. 保留原取消请求测试，但名称和说明准确描述其覆盖范围。
2. 在独立测试库创建临时测试触发器：对指定 Finding 的 `BEFORE UPDATE` 执行故障注入。触发器先查询同事务内已插入的预期审核历史，确认存在后再抛出一个可识别的异常；未看到预期历史时抛出不同异常，测试不得把两种情况都当作成功。
3. 调用真实 `ReviewFinding`，断言得到预期中途故障；再从事务外连接查询，确认新增历史为 0，Finding 状态、版本、最后审核人/时间/理由均与调用前相同，证据不变。
4. 用 `t.Cleanup` 清理触发器和函数，即使测试失败也执行；不要改服务生产代码增加全局失败开关。
5. 移除注入后重试同一业务请求，确认能正常完成一次审核，证明没有留下幂等键或连接状态残留。
