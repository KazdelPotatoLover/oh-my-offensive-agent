# 第三阶段：Planner、Worker 与最小证据闭环

本文是新项目的设计与实现任务，不是 ARTEX 现有实现说明。目标是把第二阶段的单 Agent 执行器扩展成可持续推进的任务系统。先跑通一个 Worker，再在同一阶段扩展到两个 Worker；沿用固定 HTTP 样本验证调度和信息回传。

## 1. 当前基线与加速方式

2026-10-20 检查基线：`dffa62f`。已经存在 FakeWorker、单 Agent 工具循环、MockProvider、真实协议适配器、消息与调用存储、预算和停止机制。后端 `go test ./... -count=1 -timeout=120s` 已在独立临时数据库中通过，测试数据库执行后已删除。没有调用真实模型，也没有验证浏览器交互或前端构建。

本阶段把原先分开的编排、共享结果、最小证据关联合并交付。暂不加入真实网络工具、Shell、MCP、向量库、图形布局、SSE 或自动恢复执行。页面继续轮询。

实现可分三个提交连续完成：会话与存储边界；单 Worker 闭环；双 Worker 与验收。每次提交保留原有 fake 与 agent 执行方式。

## 2. 最重要的结构变化

```text
Task：用户保存的任务定义
  └─ Run：一次完整执行，由 Engine 管理生命周期与总预算
       ├─ PlannerRound：一次规划，有独立 AgentSession
       ├─ WorkItem：要做的一件工作，保存依赖和稳定去重键
       │    └─ Attempt：这件工作的某次执行，有独立 AgentSession
       ├─ Observation：结构化观察，关联原始工具调用
       └─ RunEvent：整个执行的活动时间线

AgentSession
  ├─ Message
  ├─ ModelCall
  └─ ToolCall
```

Run 负责一次整体执行；Session 负责一段模型对话；WorkItem 负责工作内容；Attempt 负责某次实际尝试。这四者不能用一个 ID 替代。

第二阶段的 AgentRunner 直接完成整个 Run。本阶段应抽出可复用的会话执行部分，让它返回结果给调用方。编排模式下，Worker 会话完成只结束 Attempt 与 WorkItem，不能直接结束整个 Run。Engine 是 Run 终态的唯一协调者。

Manager 保留为进程内执行器注册、取消和等待组件；它不承担业务规划。先保持单个后端实例，不宣称具备多实例协调能力。

## 3. 需要理解的执行过程

```text
Engine 启动一次 Run
→ 创建 PlannerRound 与 Planner Session
→ Planner 读取目标、工作状态、已有观察，提交计划或结束建议
→ 程序校验计划并事务提交
→ Worker 原子领取依赖满足的 WorkItem，创建 Attempt 与 Session
→ 执行现有样本工具，保存原始输出和结构化观察
→ Attempt 与 WorkItem 收尾，通知 Engine 有变化
→ Engine 合并短时间内的通知，再启动一轮规划
→ 校验结束条件并生成最终输出
```

每轮 Planner 使用新会话，必要上下文从数据库构建。跨轮计划与待办保存在 WorkItem 中，而不是只保留在聊天内容或内存里。

图谱不是本阶段的前置条件：工作依赖表与观察来源关系已经提供最小的关系结构，后续再增加资产和探索图。

## 4. 最小数据模型与迁移

建议至少增加以下对象，字段命名可由实现 Agent 按现有风格调整：

| 对象 | 必须表达的信息 |
| --- | --- |
| AgentSession | run_id、角色、关联规划轮次或 Attempt、状态、输入快照、结束原因 |
| PlannerRound | run_id、轮次、触发原因、session_id、规划结果、状态 |
| WorkItem | run_id、稳定 key、目标、状态、结构化输入、输出、当前 Attempt |
| WorkDependency | 工作与前置工作的关系；禁止自依赖、跨 Run 依赖和环 |
| Attempt | work_item_id、尝试序号、session_id、状态、起止时间、结束原因 |
| Observation | run_id、attempt_id、类型、内容、来源 tool_call_id |

消息按 Session 排序；模型轮次按 Session 计数。工具调用在服务端使用数据库主键，模型生成的 call_id 只在所属请求或会话上下文中解释，不能当全局唯一 ID。

迁移应为旧 agent Run 回填 legacy Session，保留旧 API、历史记录和既有测试。可以保留 run_id 方便查询，但校验 session_id 与 run_id 一致。原有 Run 事件仍按 Run 全局排序，并增加 session_id、work_item_id、attempt_id 等定位字段。

当前 `agent_messages` 使用 Run 内 `MAX(seq)+1`。两个会话并发后不能直接共享这个序号生成方式：会话内序号需要受锁或原子计数保护，Run 事件序号也需要串行分配。

## 5. Planner 的接口与权限

第一版选择一种提交计划方式即可：例如提供 `submit_plan` 领域工具，参数是结构化计划，而不是从自由文本中猜任务。

每项计划包含稳定的工作 key、目标、结构化输入与依赖 key。Planner 可读工作列表、已有观察和必要工具输出，可提交新工作与结束建议。本阶段不能直接调用读取样本的执行工具。

程序负责校验：

- 工作 key、目标与输入满足约定格式；输入样本 ID 在 Run 范围内。
- `(run_id, key)` 唯一。重交相同定义返回已有工作，不重复创建；相同 key 配不同目标、依赖或输入则报告冲突。
- 依赖只能指向当前 Run 已有工作或本批新工作，不允许形成环。
- 一轮提交的计划、关系和事件要么一起成功，要么一起失败。
- Run 已在停止或终态时，禁止接受新计划。
- 超出总工作数、规划轮次或预算时，不继续派工。

语义相同但换了 key 的任务，不能仅靠唯一索引彻底去重。本阶段依靠结构化任务类型、明确样本 ID 与总量上限控制，不宣称实现通用语义去重。

## 6. Worker 的边界

Worker 只能领取一项具体工作，读取相关输入与前置结果，执行允许的工具，提交结果后退出。新方向交给下一轮 Planner 决策。

工作状态可采用 `pending / running / completed / failed / cancelled / blocked`。仅当前置工作全部 completed 时才允许领取；前置工作 failed、cancelled 或 blocked 时，依赖工作应有明确阻塞原因。

领取时，在同一短事务中检查 Run 仍可执行、选择可领取工作、更新状态并创建 Attempt。并发领取由数据库保证只有一个成功，不能依靠先查询再无条件更新。事务期间不调用模型或执行工具。

本阶段每项工作最多一个 Attempt，不自动重试。Attempt 与 WorkItem 仍分开建模，为后续重试留出空间。不要提前加入租约接管或崩溃后重放；启动时沿用 interrupted 规则，收尾遗留 Session 与 Attempt。

## 7. 观察和证据

工具原始输出先由宿主程序保存，再允许 Worker 通过 `record_observation` 这样的领域工具提交结构化观察。Observation 必须引用当前 Attempt 中已成功执行的真实工具调用；服务端校验归属与状态。

模型提交的文字是解释。保存了真实来源，只能证明这条解释来自某次输出，并不能自动证明解释正确。界面区分原始输出、观察与待验证推测。

本阶段复用现有数据库中的工具输出作为证据，不另建文件系统或对象存储。原始证据与展示摘要分开；若输出被截断，应记录截断标记和原始大小。练习样本很小，不需要为此搭建大文件系统。

## 8. 必须先处理的存储问题

当前 AgentRunner 的部分消息、调用更新与事件写入没有检查错误。新增编排前，应检查所有关键持久化操作：

- 保存模型工具请求失败后，不继续执行相关工具。
- 工具已经执行但保存结果失败时，不继续请求模型、不宣称完成、不自动重放工具。
- 如果数据库暂不可用，停止调度并写结构化日志；数据库恢复后，在限定时间内尝试记录 `persistence_error`。若无法写库，明确只能由后续启动恢复终结，不能假装已经保存失败状态。
- 短事务内原子保存状态和对应事件；模型或工具等待期间不持有事务。

这不是要求在本阶段实现分布式事务；它是在不确定时停止扩大影响。

## 9. 停止、预算和完成

Run 停止后，先持久化 stopping，禁止新规划和新领取，再取消当前 Planner 与所有 Worker。所有执行退出、子状态收尾后，Run 才进入 stopped。迟到结果不能改写终态或继续派工。

总预算属于 Run，每个 Session 另有局部上限。沿用现有预算字段，但让总模型调用、总工具请求和总时间覆盖 Planner 与所有 Worker。并发调用前原子预留计数；被拒绝的工具请求也消耗请求预算。

建议演示默认上限：8 个 PlannerRound、12 个 WorkItem、2 个 Worker；总模型/工具次数与总时间保持可配置。达到上限时保留部分成果，明确 budget_exhausted，不能写成目标已验证。

完成条件由 Engine 检查：没有运行中的规划和 Worker，没有可执行或等待中的工作，并且存在有效的结束建议与最终输出。Planner 在还有活动工作时建议结束，本阶段返回冲突让它后续再判断，不隐式取消工作。

队列为空本身不代表目标完成。最终结果单独表达 complete、partial 或 blocked 等业务结论，Run completed 仅表示流程正常结束。工作失败或前置缺失不能被报告成“全部分析完成”。不要仅因模型回答中出现“完成”就结束 Run。

## 10. 固定验收练习

继续分析现有三个 HTTP 响应样本：

1. Planner 派出三个独立读取与整理工作，每项对应一个样本 ID。
2. 派出一个汇总工作，依赖前面三项。
3. 先以一个 Worker 依次完成，再设置两个 Worker 并行处理。
4. 每项读取工作记录状态码、标题与真实来源调用 ID。
5. 汇总工作只读取前置观察与相关证据，不重新请求样本工具；系统必须按角色与任务限制工具集合。
6. Planner 看到结果后给出结束建议；Engine 校验并保存最终报告。

Mock 脚本用于确定性验证调度与依赖，不得因为是 Mock 模式就在 Engine 中写死业务顺序。真实模式使用同一业务路径；没有真实服务验证时明确标注未验证，不自动退回 Mock。

## 11. 最小验收矩阵

| 场景 | 需要证明的行为 |
| --- | --- |
| 完整闭环 | 规划、派工、执行、观察、下一轮规划和汇总都可追溯 |
| 双 Worker | 可并行，但同一 WorkItem 只被领取一次 |
| 会话隔离 | 不同角色、轮次与 Attempt 的消息不混在同一对话里 |
| 重复提交 | 同 key 同内容复用；不同内容冲突；无部分提交残留 |
| 错误依赖 | 自依赖、环和跨 Run 引用被拒绝；前置失败有阻塞原因 |
| 证据归属 | 伪造、跨 Run 或跨 Attempt 的来源 ID 被拒绝 |
| 全局预算 | 两个 Worker 共享总额度，不能各拿一份完整 Run 预算 |
| 停止竞争 | stopping 后不再派工；迟到结果不能覆盖终态 |
| 重启 | Run、Session、Attempt 和未执行工作状态一致收尾；不重放 |
| 持久化故障 | 关键记录失败后不继续执行或误报完成 |
| 兼容 | 第一、二阶段测试与历史页面继续工作 |

前端在 Run 详情增加工作列表：目标、依赖、状态、Attempt、所属 Session，以及观察来源入口。继续显示事件、消息、调用和最终报告。使用列表即可，不做图布局。

## 12. 交给实现 Agent 的任务

在本项目完成上述第三阶段，先阅读前两阶段文档与当前实现。连续完成会话隔离、单 Worker 闭环、两个 Worker 并发与验收，保持每个提交可运行。

重点按本文定义实现 AgentSession、PlannerRound、WorkItem、WorkDependency、Attempt、Observation，抽离会话执行器与 Run 生命周期，修正关键持久化错误处理。复用现有 Provider、工具协议、Manager、预算与状态服务，不另建一套平行系统。

以固定样本练习验证完整闭环，Planner 仅有规划与查询权限，Worker 按工作类型获取工具。全局预算、原子领取、终态保护、事件一致性和旧数据迁移必须落实在程序与数据库中。

交付模块职责、关键数据关系、实际迁移、测试命令和结果、页面使用方式、未验证部分。数据库测试必须使用明确配置的独立 TEST_DATABASE_URL，不得清空开发数据库。真实模型验证单列；本阶段不引入真实网络工具和后续扩展系统。

学习验收：项目负责人应能解释 Run 与 Session 的区别、为什么 Worker 完成不等于 Run 完成、依赖与领取由谁保证、证据 ID 为什么要校验，以及预算为何必须在 Run 级共享。
