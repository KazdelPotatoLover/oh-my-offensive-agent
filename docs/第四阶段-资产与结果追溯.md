# 第四阶段：资产与结果追溯

## 1. 这一阶段做成什么

现在系统能规划工作、执行工具和保存观察。下一步让用户能从一个被分析的对象出发，看到它在历次运行中经历了什么，并沿着来源找到原始工具输出。

本阶段的交付用一句话描述：打开“登录页样本”，能看到哪些 Run 分析过它、产生了哪些观察，以及这些观察为什么引出了后续工作。

代码检查基线为 `e485498`。第三阶段后端测试已在独立临时数据库中运行通过，临时数据库已删除。本次没有验证真实模型、前端构建或浏览器交互。本文是下一阶段任务，不代表本阶段已经实现。

## 2. 用现有练习理解流程

```text
Run 启动，按输入范围关联三个样本资产
→ Planner 派发分析工作，每项工作关联具体资产
→ Worker 读取样本，保存关联资产的观察和原始来源
→ Planner 读取观察，必要时派发后续工作并引用触发它的观察
→ 用户从资产详情查看本轮及历史 Run 的分析记录
```

资产表示“分析的对象”，观察表示“这次实际看到了什么”。同一资产可以在两次 Run 中出现，两次观察仍是不同记录。

另一个区别：工作依赖表示“要等谁完成”；来源关系表示“为什么安排它”。一项汇总工作依赖三个分析工作，但依赖关系并不能代替具体观察的来源关系。

## 3. 范围

继续使用三个内置 HTTP 样本和现有 Provider、工具循环、Engine。增加资产列表、资产详情与来源展开。继续使用 PostgreSQL 和前端轮询。

本阶段不加入真实网络访问、扫描、Shell、自动漏洞确认、漏洞库或复杂图形布局。样本分析产生的是观察，页面标题或响应头本身不能作为漏洞结论。

## 4. 最小数据关系

建议新增以下关系，具体命名可按现有代码风格调整：

| 记录 | 含义 |
| --- | --- |
| Asset | 跨 Run 保持稳定的对象身份 |
| RunAsset | 本次 Run 范围内的资产，以及执行开始时的非敏感描述快照 |
| WorkItemAsset | 具体工作面向哪些资产；汇总可以面向多个资产 |
| WorkItemSource | 某项工作由哪些已有 Observation 引出 |

Observation 增加可空 asset_id；旧数据保留为空。WorkItem 增加可空 created_by_planner_round_id；新增编排工作由服务端填写真实创建轮次，不能让模型指定。

Asset 与 Run 通过 RunAsset 关联。WorkItem、Observation、Session 和调用仍保留现有 Run 归属。不要把历史数据迁移成猜测的资产绑定。

这就是最小的资产与探索关系。存成表和关联就能完成追溯，暂时无需独立图数据库或统一的通用图节点表。

## 5. 资产身份由程序确定

本阶段只实现一种资产 `sample_endpoint`。使用服务端白名单里的 namespace 与 external_key 生成稳定身份，例如：

```text
namespace = builtin-http-v1
external_key = sample_login
kind = sample_endpoint
```

对 `(namespace, kind, external_key)` 建唯一约束；多个 Run 或并发导入不能生成重复资产。显示名和描述可更新，但身份不随标题变化。

namespace 区分不同样本集。未来真实 URL 资产会有自己的规范化规则，不能把样本身份当成真实站点身份。

启动 Run 时，从不可变 scope 快照解析允许的样本 ID，校验白名单，在同一业务提交中 upsert 资产并写 RunAsset。旧请求的 scope 字段存在不同历史形式时，为已支持的格式提供确定的适配，并保留旧测试；不要把无法识别的范围默认为全部样本。

资产库共享身份，执行范围来自 RunAsset。资产库中存在某个对象，不代表当前 Run 允许分析它。本阶段维持单个本地工作台的使用方式，不宣称已有多租户隔离。

## 6. 接入已有 Planner 与 Worker

给 Planner 增加只读的当前 Run 资产查询；submit_plan 的项目增加 asset_ids 和 source_observation_ids，两个字段均作为结构化参数校验。

- asset_ids 必须属于当前 RunAsset；输入 sample_id 必须与关联资产一致。
- source_observation_ids 必须引用当前 Run 中已经存在的观察。首次工作没有观察来源时，显示“来自本次目标”，不要伪造来源。
- 观察来源和工作依赖分开保存，分别展示。汇总仍使用依赖保证执行顺序。
- 同 key 重交时，资产与来源集合也参与等价性校验；列表顺序不同但集合相同应视为相同。
- 工作、依赖、资产关联、来源关联和对应事件在短事务中一起提交，错误时全部回滚。
- stopping 或终态 Run 不再接受新工作与新观察；保留第三阶段的停止收尾规则。

旧的 fake 和单 Agent 模式继续工作；没有声明资产关联的历史工作显示“未关联”，不被反向补造来源。新版编排演示明确提供资产关联。

## 7. 观察必须属于正确的资产与调用

Worker 记录观察时，服务端验证：

1. Observation、Attempt、Session、ToolCall 与资产关联属于允许的同一个 Run。
2. source_tool_call_id 对应当前 Attempt 的成功调用。
3. 该调用实际执行了 read_sample，其 sample_id 与观察绑定的样本资产一致。
4. 该资产在当前工作关联与 Run 范围内。

不要仅验证“ID 存在”。同一 Run 中，不能把读取首页的输出绑定成登录页的证据。

目前 record_observation 支持 UUID 和模型 call_id 两种输入。UUID 必须检查归属；若继续支持 call_id，查找必须限定当前 Session，不能先从整个 Run 找到第一条同名调用。模型调用 ID 不能作为全局唯一标识。

模型提交的观察文字仍需人工判断。来源有效只表示可追溯，不意味着自动验证了文字结论。原始工具输出保持不变，跨 Run 的新观察不能覆盖旧观察。

## 8. 用户界面

新增资产列表：显示三个样本资产及关联 Run 数量。

资产详情按 Run 分组，显示工作、工作状态和观察；每条观察可展开来源 ToolCall，查看真实参数、输出、状态和时间。Run 详情增加关联资产，WorkItem 详情增加“创建轮次”“来源观察”和“前置依赖”。缺少关联的旧数据明确显示未关联。

当前 API 没有资产查询入口，应新增相应接口；用列表与展开详情即可。不要添加“安全覆盖率”或把有一条观察显示为“已全面测试”。可以显示客观的工作数、观察数与历次 Run。

## 9. 固定演示

1. 按第三阶段流程分析首页、登录页、健康检查三个样本并汇总。
2. 在新一轮 Planner 中，引用登录页标题观察，提交一次固定 key 的标题复核工作；这一小步仅用于演示来源链。
3. Worker 再次读取对应样本，记录新观察；Planner 查看已有工作，不能无限重复派发。
4. 最终报告引用真实 Observation ID；用户能沿报告或工作列表打开原始输出。来源链接或引用索引由服务端校验，不能把模型写的任意链接直接当有效证据。
5. 再运行一次同样任务：资产仍是三个，Run、工作和观察有各自的新记录。

Mock 与真实 Provider 共用业务路径。更新必要的演示预算以覆盖新增工作，仍须遵守 Run 总预算。真实服务未测试时单列说明。

交给实现 Agent：在本项目完成本阶段，阅读前序文档并沿用现有数据与服务。增加版本化迁移、必要查询和领域工具、前端资产视图与来源展开，保持原有模式与历史数据可读。

- 后续工作的观察来源可以展开；依赖与来源两种关系展示正确。
- 停止竞争、重启收尾、全局预算与原有测试继续通过。
- 新迁移保留旧 Run；不猜测补齐旧资产、旧观察和创建轮次。

数据库测试只使用独立 TEST_DATABASE_URL。交付实际验证结果、页面入口、数据关系和未验证部分。本阶段只实现资产与追溯，不提前实现下一阶段的真实工具。
