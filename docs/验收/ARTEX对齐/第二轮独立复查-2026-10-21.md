## 1. 四项已复现的缺陷

| 反例 | 预期 | 实际 |
| --- | --- | --- |
| TestReview2Probe_RejectEvidenceFromAnotherAsset | 资产 A 的源工具不能用于资产 B 的 empirical Finding | 接受并保存为 verified |
| TestReview2Probe_RejectOldEpochEvidence | epoch 1 的源工具不应冒充 epoch 2 的实证来源 | 新 epoch 接受旧工具 |
| TestReview2Probe_RejectTextOnlyVerifiedFact | 无工具/观察来源的任意文本不能直接获得 verified | observed + 任意非空 evidence 字符串即 verified |
| TestReview2Probe_NoFixedVerdictWithoutTools | 没有实际验证工具执行时，不得判已修复 | 工具调用数为 0，凭模型文本保存 fixed |

这些是输入边界/结果可信度反例。用合成工具记录准备测试数据是为隔离校验边界，不声称做过真实漏洞验证；复测反例明确验证没有任何工具执行时不应得出确定结论。

### 来源校验根因

`backend/internal/service/retest.go:105` 读取源调用的“代次”时，查询的是关联 Run 当前 current_epoch，而不是 agent_tool_calls.epoch_number；同 Run 下比较自然一直相等。还未验证源调用参数/真实输出资产等于 Finding 目标资产，以及活动 Attempt/Session 与写入者的关系。

应读取真实源记录的代次，校验资产、调用状态、执行上下文和可信证据内容；任意成功工具 ID 不等于实证漏洞。总执行恢复时可复用历史证据的授权策略要单独定义，不能把旧代次伪装为当前。

### Fact 与目标判断根因

`service/exploration.go` 的 RecordFact 依据 confidence=observed 且 evidence 非空直接写 verified。evidence 仍是自由文本，没有真实来源 ID 验证；ProveGoal 的 verified 状态门槛因此可被自述绕过。应保留文本说明，但通过真实工具/观察引用建立证据边界，再按目标验收规则判断。

### 复测判断根因

`orchestration/retest.go` 用最终文本中的 reproduced/vulnerable/fixed 等子串判结果，未要求实际工具证据。否定句如 not vulnerable 也会被 vulnerable 子串误判。

provider=nil 的分支甚至直接按旧 verification_state=verified 推断 still_reproducible，未访问目标。应返回明确未执行/无法确认，不能称真实复测。

## 2. 仍未接通或未满足契约的路径

### 创建复测 API 仍未调度 RetestExecutor

`handler/run.go:1346` 创建记录后直接返回。检索 NewRetestExecutor/ExecuteFindingRetest，生产调用仍没有连接创建入口；仅新增审计测试直接构造执行器调用。

该测试传入 nil Registry，假 Provider 直接返回一句 fixed，没有工具请求。这证明执行器能处理文本，不证明完成独立工具验证。需要真实启动、取消、预算、重启以及证据提交链路。

### 预算刷新和时间追加尚未生效于活动执行

RefreshBudget 定义在 engine.go，但没有生产调用方；只有构造 NewEngine 时读取 grants。Handler 写账本后没有更新活动 Engine。

即使调用 UpdateEffectiveBudget，Engine.Run 的 runCtx 仍由开始时的 WithDeadline 创建，不会因改 BudgetManager.deadline 自动延长。预算耗尽的 stopped Run 恢复也没有统一资格、授权、启动与代次操作。

### Epoch 仍未保护完整生命周期

StartNewEpoch 仍可直接改 current_epoch、关闭 Session 并设置 running，未撤销旧 Engine/context，也未正确重排旧 running WorkItem。旧 epoch 统一写 completed 会损害历史语义。

Engine 没有绑定执行 epoch，FinalizeRunWrapup 没有 expected_epoch 条件，Manager 注册/释放仍只按 runID。精确比较 ValidateEpoch 虽然修正，但不能替代这些链路保护。

### 暂停仅在部分边界生效

Engine.Pause 只设置标志；Worker 的 BeforeTurnHook 在下一模型轮次检查。暂停后已在等待的模型若返回工具调用，同轮工具循环没有暂停屏障，仍可能启动工具；Planner 的模型会话也未接相同屏障。

应定义“请求暂停”和“已暂停”的确认语义，对模型返回后的工具准入同样检查，并验证在途执行/全局停止竞争。当前同步返回 paused 不足以保证暂停期间无新模型/工具请求。

### 工作空间、产物、压缩和 profile 仍缺实际实现证据

本轮未找到生产工作空间/产物读取/压缩检查点/profile 配置实现；trace 检索与工具输出截断不能代替这些能力。进度文档仍不应将其全部标为已落地。

## 3. 新审计测试覆盖范围仍被夸大

- UnifiedScheduling 测试直接调用 Claim/LoadConversation/FinishWorkItem，没有实际运行 Engine 完成第二轮。
- ExecutionControl 测试以随机、不存在的 WorkItem ID 调用 steer/kill，未断言目标真实 Worker 被取消、纠偏进入模型消息，也未验证暂停后无工具执行。
- Epoch 测试主要显式调用 ValidateEpoch，未覆盖旧 Engine 最终化及 Manager 释放。
- Retest 测试没有工具调用却断言 fixed，正好展示了上面的可信度缺陷。

需要将这些用例保留为服务测试，并另补真实执行链反例；不能仅按 TestAudit 名称判断验收层级。
