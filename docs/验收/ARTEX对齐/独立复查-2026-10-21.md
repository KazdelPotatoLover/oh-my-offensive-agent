# ARTEX 对齐改造独立复查

复查日期：2026-10-21。基线提交 `74019b6`，审查对象为其上尚未提交的 P0–P7 实现。本文是独立复查结论，不覆盖原实现者的测试记录。

## 当前结论

新增了局部预算、跨 Attempt 消息加载、探索节点/边/锚点、过程检索、控制与复测 API、前端面板等实现，具有可复用基础。但不能接受“P0–P7 全部完成、无缺口”的总验收结论：多条核心能力未连接真实执行路径，部分验收测试只验证手工构造状态及服务返回。

下面发现来自实际调用关系和源码，不因已有专项测试 PASS 而自动消除。

## 1. 续跑创建了活动记录，却未调度执行（阻断 P1）

- `service/agent.go:1376` 的 ContinueWorkItem 直接新建 running Attempt/Session，将工作置 running。
- `handler/run.go:648` 调用后直接返回，没有启动/通知执行器。
- Engine 只通过 ClaimNextPendingWorkItem 领取 pending 工作；上述 running 工作不会进入该领取路径。
- Planner 注册表也没有结构化继续/重试工具。PlannerTodo 虽有表和服务，却未注入 Planner 提示或工具。

结果：接口显示“继续成功”不等于 Worker 继续执行，可能再次形成悬挂工作。需让继续操作进入统一可认领队列，或通过统一执行器原子启动；不要双重创建 Attempt。验收必须由真实 Engine 自动跑到新结果，不能测试里再手工 FinishWorkItem。

## 2. 暂停、终止和纠偏未接运行控制（阻断 P5）

- `service/control.go:21` PauseRun 主要将 runs.status 改为 paused；ResumeRun 主要改回 running。
- 对应 Handler 不调用 Manager/Engine 的取消、暂停屏障或恢复启动。
- KillWorkItem 修改工作/Attempt/Session 终态，但没有取消正在执行的模型/工具 context。
- SteerWorkItem 直接修改 objective/input_data；已在运行的 Worker 使用启动时内存快照，没有读取该更改的安全检查点。
- 018 迁移加入 paused 状态，未将它加入旧的同 Task 活动 Run 唯一索引条件，数据库约束与 IsActive 定义不一致。

结果：页面状态可能变化，但已在执行的工具未被中止，纠偏无法保证送达当前轮次。需使用统一控制服务与执行器的实际 context/消息通道；状态变化与生效确认分开，保持原任务快照。

## 3. Epoch 只做了局部字段检查，没有形成执行隔离（阻断 P5）

- `service/control.go:319` StartNewEpoch 未验证准入/活动工作/旧 Engine 状态，直接提高 epoch 并设置 Run running；旧 epoch 统一写 completed 也可能改错历史原因。
- `ValidateEpoch` 只拒绝 caller < current，未来 epoch 不被拒绝；它没有被 Engine/Manager/统一 Finalize 链路使用。
- 部分新建 ToolCall/FinishWorkItem 检查 epoch，但模型调用、已有工具结果更新、知识写入、Run 最终化和旧 Manager 清理没有全面隔离。
- Manager 仍按 runID 注册和释放，未带 epoch。

结果：不能宣称旧执行不会影响恢复后的新执行。需把代次作为执行器、准入、事务写入和最终化的统一条件，而不是独立调用一次 ValidateEpoch 就认为完成。

## 4. 追加预算有账本，尚未影响运行预算（阻断 P5）

- GetEffectiveBudget 的调用方为读取 API，Engine 没有使用它重建/更新预算与 deadline。
- GrantBudget 的 ON CONFLICT 更新 reason，不比较同键请求额度；同键不同内容未按契约返回冲突，还会修改旧授权理由。
- ResumeRun 只允许 paused，不会为预算耗尽 stopped Run 完整恢复执行。

结果：页面可显示追加额度，运行中的 BudgetManager 仍执行原配置。需将新授权、恢复代次、有效预算、剩余量和真实调度连成事务/启动链路，避免重置累计用量。

## 5. 实证发现与事实来源校验倒退（高优先级）

- `service/retest.go:38` ReportFinding 主要检查标题、资产 ID、source_kind 和 Run 存在。
- 调用方填写 empirical 即写 verification_state=verified；证据默认可为空，没有验证活动 Attempt/Session、资产 Run 范围和实际成功源工具归属。
- 为兼容列表，它会直接插入一个 needs_attention CheckResult，但这不代表注册检查实际执行过。
- RecordFact 接受自由文本 evidence，统一插入 verified 状态；ProveGoal 主要核对节点类型及 Run，未核验验收条件、证据状态/置信、撤回与证明失效。

结果：模型/请求方自述可被保存为已验证结论并用于证明目标，违背既有证据边界。需区分“Agent 自述/推测”和“有实际来源的证据”，先保住来源和执行上下文，再建立可审查的目标判断。不能用无来源文本生成实证标签。

## 6. 新目标、意图和知识体系尚未完整接入（P2/P3 部分完成）

- 增加 intent enum 和通用工具分支，但原 plannerContract 仍要求固定工作类型，未完整教会新知识/意图模型。
- 未见执行 profile 注册/配置与能力选择，仍主要通过 work_type switch 固定工具集。
- suggest_completion 只在成功查到非空 Goals 时检查；零目标和查询失败会跳过证明守卫，未区分新探索模式与旧模式。
- Fact 缺少完整状态/版本/撤回与 Goal 证明失效机制；已有表和边不能代替这些行为。

## 7. 复测是记录生命周期，尚未实际执行（阻断 P6）

CreateFindingRetest 插入 running verifier Session/retest，Handler 直接返回；未调度 Provider/SessionRunner 或独立复测执行器。FinishFindingRetest 由 API 接收 verdict/evidence/summary 完成记录。

这是复测记录管理，不能当作“独立 Agent 已复测并验证修复”。需要接真实本地工具与执行链，在完成后以实际源证据写入结果，并覆盖停止/失败/重启。

## 8. P4/P7 交付与声明不符

trace 检索已有实现，前端已有面板，但未看到受控工作空间、完整产物存储与读取、压缩检查点/上下文恢复，以及可配置执行 profile 和另一条工具流量关联链路的完整实现。

P7 动态工具测试手工创建 Registry 并运行 SessionRunner，只证明注册接口能使用自定义测试工具；该 Registry 能力原本就存在，不能单独证明新 profile/能力配置已接生产 Engine。

## 9. 测试证据应重新分级

`TestP7_EndToEndAlignmentLifecycle` 手工将 Run UPDATE 为 running，直接调用 report_finding，并由请求体直接提交复测 verdict，再调用 ProveGoal。这个用例可以验证服务组合，不能证明 Planner→Worker→真实采集→复测执行→目标达成的完整 Engine 链。

P5 暂停/恢复测试主要验证数据库状态与认领拒绝，未验证正在执行的模型/工具被暂停。Epoch 测试主要显式调用 ValidateEpoch，未覆盖旧 Engine/Manager 的真实迟到路径。

因此“25 项专项通过”不等于总计划 E1–E14 全部通过。需补核心反例，并将进度清单中超出证据的“已完成/无缺口”修正为部分实现/待集成。

## 建议修复顺序

1. 暂停发布新功能，先接通 Continue/Retry 与统一执行器，防悬挂；接通 pause/kill/steer 的真实控制。
2. 恢复 ReportFinding/Fact/Goal 的来源、范围、执行与可信度边界。
3. 统一 epoch、预算授权、Manager 生命周期和最终化，补并发与迟到路径测试。
4. 将 Todo/目标/开放意图/profile 接到 Planner 实际上下文和工具。
5. 接实际复测执行，再补工作空间/压缩/能力扩展及浏览器完整验收。

不建议在当前状态直接提交为“ARTEX 对齐完成”或部署覆盖正在使用的服务。本轮未改实现代码或开发库，也未运行真实模型/靶场。
