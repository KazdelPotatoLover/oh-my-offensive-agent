## 1. 两个残余证据边界已独立复现

### 1.1 没有目标绑定的工具仍能作为实证来源

`service/retest.go:127` 只在参数/输出出现 asset_id 或 asset_ids 且冲突时拒绝。两者都没有资产信息、也没有相关观察时，仍走到 verification_state=verified。

独立反例 `TestReview3Probe_RejectUnboundEmpiricalSource`：将一条成功工具设为 list_facts、参数 {}、输出 []，用它为范围内某资产创建 empirical Finding，仍被接受并写 verified。

这与“给 A 证据用于 B”的上一反例属于同一问题：来源需正向证明绑定目标，不能只在发现某个已知冲突时拒绝。修复应统一解析受支持工具的证据来源/类型/资产与执行资格；无法证明归属的记录不可作为实证来源。工具成功不等于发现成立，证据说明和 Agent 判断应保留可审查界限。

### 1.2 任意成功工具仍能解锁 fixed 复测结论

`orchestration/retest.go:111` 仅统计本 Session 的成功工具总数，只要大于零，继续用最终文本的 fixed/vulnerable 等子串决定结果，没有绑定目标及验证动作。

独立反例 `TestReview3Probe_NoFixedFromNonVerificationTool`：假 Provider 仅执行 list_facts，再输出 fixed。数据库证明没有 get_endpoint 调用、没有访问目标，最终仍将 Finding 记为 fixed。

上一轮“完全零工具”反例被修复，但“读了内部事实就算验证目标”仍被放行。应使用带本次实际验证调用引用的结构化结果，校验工具类别、资产、Session、成功状态和判定条件；证据不足或不相关一律 inconclusive。自然语言说明保留，不能用子串当裁决协议。

## 2. 执行代次恢复仍有完整性缺口（静态审查）

`handler/run.go:1297` 先 StartNewEpoch，再 RevokeEpoch 取消旧执行，然后直接返回；没有创建和注册新 Engine 的路径。服务层同时把 Run 设置 running，并关闭旧 Attempt/Session，但没有完整重排旧 running WorkItem。

因此旧执行撤销/旧 Finalize 拒绝虽有改进，“提高 epoch 后任务继续执行”尚未完成。应把授权/资格校验、旧执行撤销、工作重新入队、新代次启动和失败收尾组织为统一恢复命令；不能让 Run 显示 running 而无执行器。现有 StaleEpochEngineRejectedOnFinalize 测试直接调用带 epoch 的最终化服务，不能证明该 API 已完成恢复。

Manager 非 ControllableExecutor 的代次、旧执行写入的全部路径及实际启动失败仍需完整验收，不能只因多了 epoch 字段就宣称所有写入隔离完成。
