## 3. 缺陷一：响应正文没有完整读完，也会返回成功

位置：`backend/internal/tools/http.go:248`。代码忽略 `io.ReadAll` 的错误。

复现 A：本地服务声称正文有 100 字节，只发出 `short` 五字节就断开。工具返回 nil error，并保存：

```text
HTTP 状态：200
error：null
saved_bytes：5
is_truncated：false
body：short
```

复现 B：本地服务先发 200 响应头和 `prefix`，随后持续等待。在读取正文期间取消上下文，工具仍返回 nil error、error=null 和未截断的六字节正文。

影响：收到响应头不表示正文读取完成。连接断开、正文超时或取消时，当前工具可能把残缺证据记录成完整成功结果。

修复要求：处理正文读取错误，保留已经取得的有界部分数据，记录稳定错误类型与“不完整”原因；从状态上区分主动达到保存上限与传输失败。保存部分数据不能把调用标记为完整成功。耗时应明确是收到响应头的耗时还是完整读取结束的耗时。

## 4. 缺陷二：给模型的输出预算截坏了存储证据

位置：`backend/internal/agent/session_runner.go:441` 与 `:453`。

复现：fixture `/large` 返回超过 64 KiB 的正文。HTTP 工具本身正确保存了 64 KiB 的正文并标记截断，生成约 66,015 字节的有效 JSON。但经过 SessionRunner 后，默认 8,192 字节的模型输出预算先截掉 outStr，再把同一个字符串写入 ToolCall.output。

实测数据库中的结果只剩约 8,237 字节，已经不是有效 JSON。页面无法正常解析 HTTP 证据，工具声明保存的 64 KiB 也无法从数据库取回。

修复要求：将两份数据分开：

- 证据存储：保存工具有界采集到的结构化结果及完整性信息。
- 模型上下文：按模型预算提供较短、格式有效的摘要或片段，并引用证据 ID。

模型输入预算不能覆盖或截坏唯一的一份原始证据。对编码、长度、截断原因作一致定义；不要把 JSON 直接截半后当结构化数据使用。

## 6. 为什么这个阶段重要

前面我们证明了：Agent 能请求工具，任务系统能保存过程。

本阶段增加的能力是：任务系统真的访问另一个正在运行的程序，并把它在某个时刻返回的内容保存为证据。

参与的角色分别是：

| 角色 | 本次负责什么 |
| --- | --- |
| 用户 | 选择本地 /health，创建任务并点击启动 |
| Engine | 创建规划轮次、协调工作与总预算、管理停止与结束 |
| Planner | 通过模型接口提交读取与汇总工作 |
| Worker | 在独立 Session 中完成领取到的工作 |
| 模型接口 | 返回要调用的工具及参数，本次由 Mock 脚本代替真实 LLM |
| get_endpoint | 程序实现的工具，检查范围并实际发出 GET |
| fixture | 独立运行的本地 HTTP 应用，返回状态与版本号 |
| 数据库 | 保存任务、工作、调用结果、观察和来源关联 |

Planner 和 Worker 表示 Agent 的业务角色；HTTP 工具和 Engine 是普通程序。fixture 则是被访问的应用。

## 7. 沿着一次实际执行理解流程

第一步，创建任务。

用户选择 /health。程序把选择解析成稳定资产：GET http://127.0.0.1:29090/health。资产身份代表目标；并没有因为创建资产就访问一次网络。

第二步，点击启动。

创建一个新的 Run，保存目标、范围、预算和资产快照。RunAsset 表达本次允许分析的对象。下次重新运行是另一个 Run，资产身份仍可相同。

第三步，规划。

Engine 启动 Planner Session，给它提供目标与当前状态。MockProvider 通过与真实模型相同的接口返回 submit_plan 请求，程序校验后保存工作。当前单端点演示实际生成两个读取工作和一个依赖它们的汇总工作，重复读取属于演示脚本问题，不是必须的架构步骤。

第四步，领取。

Worker 通过数据库原子领取一项可执行工作，创建 Attempt 和 Session。领取明确本次执行的归属，Session 保存这段独立对话。

第五步，模型请求工具。

Worker 的模型接口返回 get_endpoint，参数是 asset_id。这个参数只是请求，网络尚未发送。程序会检查工具权限、Run 范围、工作关联，再从快照解析固定 URL。

第六步，程序实际请求。

get_endpoint 创建 HTTP 请求并发给 fixture。fixture 返回 200、响应头及正文，例如：

```json
{"status":"UP","version":"review-v2"}
```

本次有效演示中 fixture 请求计数确实增加；这就是“工具真正运行”的证据。MockProvider 没有伪造这份 HTTP 响应。

第七步，保存工具结果。

系统保存 ToolCall，包括请求的 URL、时间、状态、响应头、正文和完整性字段。正常小响应目前工作正常；正文读取错误和大证据路径存在上面已复现的问题。

第八步，记录观察。

模型接口读到工具结果后提交 record_observation，例如“Health check reported version review-v2”，并引用真实 ToolCall。程序检查来源归属，再把 Observation 关联到资产和 Attempt。

原始响应记录应用返回的内容；Observation 是从响应中整理出的解释；最终报告则汇总这些观察。来源有效能够支持人工复核，但不能自动保证所有解释正确。

第九步，汇总并结束。

读取工作完成后，汇总工作才能开始。它使用已有观察生成报告。Planner 建议结束，Engine 检查状态，保存最终结果。completed 表达执行流程正常结束；关于系统安全性的判断仍需要额外验证方法和证据。

## 8. 为什么两次运行是有用的验收

第一次返回 review-v1，第二次返回 review-v2；两次 Run 关联同一个资产 UUID，分别拥有自己的 ToolCall 和 Observation。修改 fixture 后，第一次存下来的证据仍然是 review-v1。

这同时检验了三件事：工具读取的是正在运行的应用；资产身份跨执行保持稳定；历史证据不会随着目标内容变化而被覆盖。

实际查看顺序：打开资产页面 → 找 review-v2 的最新执行 → 展开 Inspect Tool Call → 看 response.body → 再向下找到 review-v1 的执行。你应看到两个时刻的响应，而不是两条指向当前网页的链接。

## 9. Mock、真实工具与能力边界

这次验证组合是“预设的模型回复 + 真实 HTTP 工具 + 真实数据库 + 实际浏览器页面”。本地 Mock 的 Token 统计不能作为真实模型账单。

未来接入真实 LLM 后，工具执行与证据存储路径应保持相同，规划与解释由模型生成。本阶段没有验证模型能否合理扩展测试、识别漏洞或控制误报。先修好已经复现的证据与错误处理问题，再增加下一项能力。
