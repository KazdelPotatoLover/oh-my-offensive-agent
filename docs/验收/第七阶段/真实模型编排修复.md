# 真实模型编排失败排查与验收

日期：2026-10-20。真实 Provider：`openai`，协议：`responses`，模型：`baizhi-cloud/deepseek-flash`。本文不包含密钥。

## 原始故障

Run：`8397b4b4-22f2-4d53-9ff9-cdb40c8e9f97`，结束原因 `tool_calls_exhausted`。

实际记录：17 次模型响应全部成功，报告用量 33,923 tokens；30 次工具调用中包含 1 次成功 submit_plan，29 次 read_sample（18 次失败、11 次参数拒绝）；get_endpoint 调用和 Observation 均为 0。

因此模型连接和 Responses 工具往返已经工作，故障在业务编排契约：

1. Planner 生成了 `crawl_page`、`frontier_reconcile` 等没有执行器的工作类型。
2. submit_plan 没有严格校验这些类型，接受了整个计划。
3. Engine 把未知类型交给默认样本 Worker，暴露了 read_sample 而非 HTTP 工具。
4. Worker 不断尝试本轮范围外的固定样本，消耗完工具预算；没有读取靶场。

## 修复

- 将工作类型约束为 `inspect_http_endpoint`、`analyze_sample`、`inspect_sample_endpoint`、`aggregate_summary`；工具 Schema 和后端都拒绝未知类型。
- HTTP 工作必须引用本 Run 的 HTTP 资产，input_data.asset_id 必须属于 asset_ids；HTTP-only Run 不接受样本分析工作。
- Engine 使用明确分支分配工具；旧版本留下的未知类型也会失败，不再回落到样本执行器。
- 给 Planner/Worker 明确说明可执行类型、输入、动态发现、真实来源 ID、依赖的含义、何时结束以及网页内容的数据身份。
- HTTP Worker 完成时必须有当前 Attempt 的实际观察；只有“无法执行”的文字不能完成工作。

## 真实验证暴露的第二处问题

第一次小范围修复验证 Run：`f4a606fb-99ad-4ace-ba44-79f64d0e5691`。

该次已经正确生成 inspect_http_endpoint 工作，get_endpoint 成功，实际首页返回 HTTP 200。但返回给模型的正文没有明确的证据引用字段，模型以 asset_id 代替 source_tool_call_id，导致 record_observation 和 extract_endpoint_links 失败。证据校验正确拒绝了错误来源，Run 因缺少实际观察失败。

继续修复：

- SessionRunner 为成功的 get_endpoint/read_sample 结果增加程序生成的 `_execution.source_tool_call_id` 和 `_execution.call_id`。
- source_tool_call_id 是实际工具调用记录的 UUID，与资产 UUID 分开；模型直接复制该字段用于记录观察和提取链接。
- 模型预览超出预算时只缩短正文，保留合法 JSON、证据 ID 和可容纳的响应信息。`_execution.result_truncated` 说明模型预览被缩短，不表示数据库中的原始 HTTP 证据被修改。
- 原始工具输出继续独立持久化，链接解析读取原始证据；原有 Session、Run、成功状态与资产范围校验保留。
- 提示词快照版本更新为 v3。
