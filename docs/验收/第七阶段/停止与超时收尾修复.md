# 停止与超时收尾修复

日期：2026-10-20。

## 故障与原因

Run `65f39598-608f-417c-ab23-0f41bce1a3bd` 于 13:49:02 启动，预算总时长为 120 秒。Worker Session `a3dbed35-6340-4fc9-9420-f33351b1f310` 的最后一次模型请求在 13:51:02 返回 context deadline exceeded。

实际是总运行超时，原实现存在以下收尾缺口：

1. Engine 直接尝试 `running → stopped`，但状态机只允许先进入 stopping。转换错误被忽略，执行器退出后数据库仍显示 running。
2. Worker 把所有 context 取消硬编码为 user_requested_stop；FinishWorkItem 又把 SessionRunner 已写入的 stopped 覆盖成 failed。
3. Stop 只通知内存执行器。执行器已经退出时，没有人继续确认停止，Run 可能继续卡在 stopping。
4. 部署后即时停止检查还复现了启动竞争：Stop 先读 queued，Worker 同时推进到 running，随后 Stop 按旧状态更新会返回 409。

## 修复

- 新增 `RunService.FinalizeCancelledRun`，用事务和 Run 行锁完成合法状态变化、状态事件和未完成子记录的收尾。超时原因写 timeout，显式用户停止写 user_requested_stop。
- 未完成 WorkItem 标记 cancelled，运行中的 Attempt/Session 标记 stopped，运行中的 PlannerRound 标记 stopped，尚未结束的模型/工具调用标记 interrupted。已完成的结果保留。
- 单 Agent 与 Engine 的取消入口复用上述事务。
- Worker 区分 DeadlineExceeded 和普通取消；FinishWorkItem 与 Run 停止共用锁，晚到的结果不能把 cancelled/stopped 改回 completed/failed。
- Session 状态更新只作用于 running，阻止迟到的失败覆盖 stopped。
- 停止接口在执行器已经退出时直接确认收尾；Manager 在执行器退出与 Stop 竞争时也提供兜底。仍保留注册前取消机制。
- Stop 的状态读取、更新和事件写入在同一事务行锁内进行，消除 queued → running 的竞争；Worker 完成与取消统一先锁 Run，再读取和锁定工作状态。

## 当前卡住数据的恢复

确认该 Run 的执行器已经退出后，使用同一服务收尾事务将 Run 恢复为 stopped / timeout。针对已证实被错误标记的 a3dbed35 Session、关联 Attempt 和 WorkItem，分别更正为 stopped / timeout、stopped / timeout、cancelled；添加 cancellation_reconciled 审计事件说明原标签及依据。

未删除工作、观察或原始工具证据，也没有重跑真实模型请求。

## 验收

独立临时测试库中执行：

```bash
go test -race ./... -skip '^TestDiscovery_RealTargetRange_' -count=1 -json -timeout=180s
go vet ./...
```

109 个测试/子测试通过，零失败。新增覆盖 Planner 总超时、Worker 总超时、手动停止、单 Agent 总超时、没有执行器时停止、停止后的晚到结果、Stop 与执行器退出竞争，以及停止与 queued → running 的竞争。测试验证任务位释放和合法状态事件；锁顺序调整后另行通过全部取消回归。

后端镜像已重建并部署。本地部署后再次用 Mock delay 验证 1 秒总超时，使 Run 和 Session 均进入 stopped / timeout；在同一 Task 上连续进行三次“启动后立即停止”，停止接口均返回 HTTP 200，并收敛到 stopped，确认任务位释放。临时冒烟任务已删除，部署后没有遗留活动 Run。

这次原任务的 120 秒预算确实已耗尽。修复解决停止收尾和原因分类；后续是否需要更长时长，应按目标页面数和实际模型耗时配置，不通过绕过停止来延长任务。
