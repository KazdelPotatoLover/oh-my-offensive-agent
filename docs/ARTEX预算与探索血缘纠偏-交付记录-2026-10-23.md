# ARTEX 预算与探索血缘纠偏：交付记录

日期：2026-10-23。本文是本轮完成声明。设计合同仍是 [修复计划](ARTEX预算与探索血缘纠偏-修复计划-2026-10-23.md)。

运行中的服务没有更新，也没有重启。现场库 `agent_workbench` 仍是 schema 32。下面的测试使用独立库和本地替身。

## 1. 改了什么

新探索任务在创建时冻结 `execution_input.execution_policy`，版本 `agent_limits.v1`。执行、恢复、Epoch、Main 和前端都以这份策略为准。`budget` 只是它的投影，不再用隐藏的 30/120/5/60 把投影里的 0 解释成小额度。

没有该版本的旧 Run 继续使用原 `BudgetConfig`。那些快照里的 0 或缺失字段仍按原默认值回落，不会变成不限。发现模式且未开启探索的创建继续使用历史有界授权（3 Worker、1800 秒、240/600）。

新探索默认：

| 维度 | 默认 |
| --- | --- |
| 并发 Worker | 3（范围仍是 1–8，显式 0 非法） |
| 任务时长 | 不限 |
| 模型 / 工具 / 规划轮 / 方向总数 | 不设硬上限 |
| Worker MaxTurns | 不限。一次成功的模型响应加它的整批工具算一轮 |
| Worker 单轮时长 | 1200 秒 |
| 局部收尾 | 独立 10 轮；v1 下没有隐藏的 15 秒收尾时钟 |
| Main | 没有累计 8 次上限，除非任务明确写了 `main_reserved_model_calls` |

正数环境变量、任务配置和本次请求仍是显式硬上限。省略表示继承；指针字段里的显式 0 表示不限。已经不限的维度再追加授权会拒绝，并返回“无需追加”。用户停止、Epoch 和范围校验仍然优先。空规划轮仍由既有事件合并和 10 分钟心跳等待，没有新增监督器。

探索图在后端保存唯一任务起点。新探索创建在同一事务写入 `fact/origin`，并连接 origin→用户目标的 `spawns`。`set_goals` 追加的目标写同一条边。没有显式知识来源的意图写 origin→intent 的 `derived_from`；有真实 fact/finding 来源则只连接那些来源。非法来源返回错误。Worker 报告 Finding 时按服务端可信 WorkItem 写 intent→finding 的 `yields`。起点不是已验证证据，不能 `proves`。已有 `begin` 根复用为唯一起点，不另插 origin。

历史图由迁移 `033_exploration_lineage` 的函数 `backfill_exploration_lineage()` 幂等回填。来源无效时写 `lineage_backfill_diagnostic`，不改原节点 ID、证据、预算、Epoch 或状态，也不制造 `proves`。

前端保留两字段创建表单。时长显示“不限时”或真实分钟数。预算显示“不设上限”。追加授权只对有界维度出现。画板把 `fact/origin` 标成“任务起点”，节点 ID 不变，边只来自后端。

## 3. 策略 JSON

旧 Run 没有 `execution_policy`。下面是无策略时仍会回落的默认预算，0 不会变成不限：

```json
{
  "max_model_calls": 30,
  "max_tool_calls": 30,
  "run_timeout_seconds": 120,
  "max_planner_rounds": 8,
  "max_work_items": 12,
  "max_parallel_workers": 1,
  "worker_max_model_calls": 5,
  "worker_max_tool_calls": 10,
  "worker_timeout_seconds": 60,
  "main_reserved_model_calls": 8
}
```

已被取代的探索默认授权仍只用于未开启探索的发现模式：

```json
{
  "max_parallel_workers": 3,
  "run_timeout_seconds": 1800,
  "max_model_calls": 240,
  "max_tool_calls": 600,
  "worker_max_model_calls": 20,

  "main_reserved_model_calls": 8
}
```

```json
{
  "schema_version": "agent_limits.v1",
  "task_timeout_seconds": 0,
  "max_parallel_workers": 3,
  "agents": {
    "worker": {"max_turns": 0, "run_timeout_seconds": 1200, "settlement_max_turns": 10},
```

## 5. 历史回填与本地更新

迁移 `033` 在升级时会调用一次 `backfill_exploration_lineage()`。函数保留在库里，可重复执行。主机没有 `psql`，容器命令是：

```bash
docker exec oh-my-offensive-agent-db-1 psql -U postgres -p 25432 -d agent_workbench -c 'SELECT backfill_exploration_lineage();'
```

这条命令没有对现场库执行。现场库仍是版本 32，函数还不存在。

本地更新需要先有迁移 033，再运行新后端。服务器启动时会迁移。新代码里的 origin 写入依赖该唯一索引；只更新程序、不迁移，探索创建会失败。只迁移、不更新程序，旧进程不会为新任务写起点。建议顺序：

```bash
docker compose up -d --build --no-deps backend frontend
```

本次没有执行。现场监听仍在 25432、23000、28080。

## 6. 当前运行服务与剩余限制

- 容器和现场库没有重启，也没有写入 `agent_workbench`。
- 正在运行的任务仍按旧代码和旧快照执行。新探索任务在该服务上仍会得到历史 240/600/30 分钟授权，直到按上一节更新。
- 不限只作用于带 `agent_limits.v1` 的新探索 Run。旧 Run、发现模式、独立复测会话保持有界。
- 共享模型并发、单次请求超时、网络间隔、隔离和输出大小限制仍然有效。
- 没有自动续租已耗尽方向，也没有把起点当成漏洞证明。
