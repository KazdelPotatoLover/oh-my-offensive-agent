## 目标怎样变成多个目标

1. 用户输入保存在 Task.objective，并进入 Run.execution_input。
2. 开启探索时，`service/run.go` 创建一条 `origin=user` 的 goal 节点，保存原始目标。
3. 初轮 Planner 根据目标、范围、工具能力和预算，决定调用 `set_goals`。工具接受 goals 数组；服务端校验文本后逐条追加 goal。
4. 这属于模型规划，没有固定要求拆成几项，也不按 Worker 数量拆。`set_goals` 当前是追加，不替换原目标，不会自动建立目标父子树。
5. Planner 另用 `submit_plan` 创建可执行 WorkItem/Intent。Goal 是要交付的结果，Intent 是具体推进方向；Dispatcher 才按 N 领取方向运行。
6. Worker 将结果保存为观察、事实或 Finding；新材料可以触发后续方向。通过 `prove_goal` 引用真实可用证据，才能把相应目标标为 met。

因此探索链是可交叉、可反馈的图：一个方向可能支持多个目标，一个目标也可能依赖多个方向的结果。

## 画板目前存在的真实性问题

主要装配代码：`frontend/src/components/workbench/WorkbenchApp.tsx` 的 graphNodes/graphEdges；布局和抽屉在 `ExplorationCanvas.tsx`。画板本身不执行规划。

### 1. 所有方向默认挂到第一个目标

工作方向使用 `nodes.find(kind === goal)` 选第一个目标，再生成 spawns 边，没有读取真实的目标关联。它展示的是前端推导的归类，不是数据库记录的“该方向由这个目标派生”。

### 2. 无法定位来源的事实默认挂到第一个方向

事实概览未提供画板所期待的 work_item_id，前端找不到时直接选择第一个 intent，补 yields 边。这会把同伴 Worker 的成果归到同一方向。

同时，后端探索边使用 intent 的 ExplorationNode UUID；前端主要用 WorkItem UUID 作为意图节点 ID。没有建立两类 ID 的映射，部分真实边找不到端点，布局时被过滤。

### 3. 每条 Finding 自动生成“证明目标”的边

前端为每个 Finding 生成 `Finding → 第一个 Goal` 的 proves 边，不要求后端存在有效证明。

实际核对时，图概览的边有 yields/derived_from，未返回任何 proves；真实页面仍画出了 4 条“证明”线。对应 4 条 Finding 都是 pending_review/unverified，内容为响应头配置关注项或重复候选。

这些连线不能解释为“已经证明目标达成”。

### 4. 状态和标题被错误替代

- fact 节点状态硬编码为 verified，而真实库中存在 unverified fact。
- Finding 标题读取 name/summary，而 API 字段为 title，导致可能统一显示“已验证漏洞”。
- Finding 处置状态与 verification_state 是不同维度，不能仅凭一个 status 展示为确认漏洞。

### 5. 布局含义容易被误读

画板按有向关系自动分列，并为布局暂时忽略回边；横向位置不是执行时间，也不是 Agent 层级。动画表示目标节点在运行，不等于该连线上的动作正在执行。

当前会保留节点拖动位置，新增节点未必立即形成新的清晰布局。画得整齐与关系正确需要分别检查。

## 建议的修正原则

1. 以真实 ExplorationNode ID 为图节点主键；WorkItem/Finding ID 作为明确的关联字段保留，做稳定映射。
2. 证明边只展示后端当前有效的 proves，包含证据来源、版本和目标；禁止根据 Finding 数量自动生成。
3. 方向产出与后续派生只用真实 yields/derived_from；缺失来源就显示为未关联，不自动连第一项。
4. 如需要展示目标与方向关系，补充明确的持久关联。仅用于归类的线应采用不同样式并标为展示关系，不能冒充因果或证明。
5. fact 状态使用后端真实状态；Finding 使用 title，并分别呈现来源类别、验证状态、处置状态和复测结果。
6. 点击节点读取真实详情、关联资产、Attempt 和证据。画板布局变化不修改执行状态。
7. 补一个最小前端反例：多个目标、两个 Worker、已验证/未验证事实、未确认 Finding、只有一条有效 proves，断言不会生成额外证明或错误归属。

## 修复交付（2026-10-23）

### ARTEX 对应源码与工程适配

已核对参考仓库实际实现，而非 mock 数据：

- `ARTEX/server/server.go:explorationGraph` 从 Store 读取实际 Nodes/Edges。

本项目沿用这条数据路径，新增 `GET /api/runs/{runID}/graph`。节点、关联 WorkItem 状态、Finding 状态和有效边在同一个 PostgreSQL 只读 repeatable-read 事务中读取。既有 `graph/overview` 仍供 Planner 的紧凑态势和资源列表使用；完整画板不会膨胀模型上下文。

这是本项目的工程适配：证明边还按既有 valid、节点版本、证据/目标状态、Finding 误报及复测修复状态过滤；没有修改执行状态或历史审计记录。

### 已修正行为

1. 统一用 ExplorationNode ID；WorkItem ID/Finding ID 只用于明确关联和查看执行记录。
2. 移除虚构根节点和全部猜测连线：不再把所有方向归到第一个目标、不再把无来源事实归给第一个 Worker、不再为每条 Finding 自动证明目标。
3. 读取完整节点集合，包含已结束方向和未验证事实，不再混合分页节点、概览最近 20 条事实与独立 Finding 请求。
4. Finding 使用真实 title，分别显示审核、验证、来源、复测状态，统称“发现”；事实保持真实验证状态。
5. 详情按当前选中的 ID 从最新快照解析，刷新后不会一直显示旧对象；展示已记录关系及证明理由，可打开关联方向执行记录。
6. 请求失败明确提示；刷新失败保留上次成功快照；相同内容不重建图；轮询等待当前请求完成后再安排下一次，避免请求交叠。
