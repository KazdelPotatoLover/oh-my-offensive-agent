# 第十阶段：学习 ARTEX 的分层预算与可恢复执行

日期：2026-10-21。实现基线：`74019b6`。本文是待实施设计，不是完成声明。

> 完整纠偏改造以 [P0–P7 总实施计划](ARTEX对齐改造-总实施计划.md) 为准。本文件作为运行时子系统细节；其中 A–C 先在 P1 建立，D 的 epoch/授权恢复在 P5 与执行控制统一交付，不先用账本扩展阻塞双图和开放意图。整体任务请使用 [总改造提示词](ARTEX对齐改造-交给编码Agent的提示词.md)。

本设计取代此前“创建关联新 Run”的阶段方案。用户目标是学习 ARTEX 的核心架构，不能仅交付一个简化的续跑按钮。

## 1. ARTEX 实际做了什么

ARTEX 用长期任务中的 intent 表示稳定探索方向。Worker 单次执行受 MaxTurns/MaxDuration 限制；耗尽后进入 settlement，保存成果，intent 标 exhausted，通知 Planner。Planner 根据实际 trace/output 决定接着探索、重派或换方向。

同一个 intent 重新打开时，Worker 使用由 exploration ID、intent ID 决定的稳定 transcript key 尝试恢复原对话；写回的 fact/asset/finding 保留。Planner 另派一个新方向不保证恢复旧 intent 的 transcript，必须与重开原 intent 区分。

相邻 ARTEX 仓库的参考入口：

| 机制 | 源码 |
| --- | --- |
| Worker 局部额度与 settlement | `agent/worker.go:424`、`:455` |
| 稳定会话标识、恢复历史 | `agent/worker.go:94`、`:500` |
| exhausted/blocked/done 分流、通知 Planner | `server/engine.go:1133` |
| Planner 根据真实进度续派 | `agent/planner.go:323` |
| 原 intent 重开，保留已有成果 | `db/exploration.go:322` |
| 人工 rerun 与任务恢复准入 | `server/server.go:1194` |
| 任务级时间夹逼、有序收尾与超时恢复 | `server/engine_timeout.go` |
| 独立收尾策略与轮次 | `agent/wrapup.go` |

MaxTurns 不是工具调用次数，一轮可以包含多个工具。没有证据表明 ARTEX 应用层采用了我们相同的全局 30 次工具硬上限。恢复对话不等于恢复工具进程，也不保证所有外部动作只执行一次。

## 2. 对应到本项目

| 职责 | ARTEX | 本项目目标 |
| --- | --- | --- |
| 持续推进的执行容器 | Task / exploration | Run；Task 仍是任务定义 |
| 稳定工作目标 | intent | WorkItem，保持 ID、输入、资产和依赖 |
| 单轮执行 | 一次 Worker Execute / SDK Query | Attempt，每次新建、独立审计 |
| 可恢复记忆 | intent transcript | 稳定 Conversation，关联多个执行 Session |
| 本轮记录 | 执行 trace | AgentSession，归属本次 Attempt |
| 规划与续派 | Planner + frontier | Planner + 可认领工作队列 |

不能把 Worker 槽位当会话身份，不能将旧 Attempt/AgentSession 从终态改回 running。稳定的是 WorkItem/Conversation，变化的是 Attempt/执行 Session。

```text
Run 仍有总预算与时间
  └─ WorkItem W
       ├─ Attempt 1 / S1 → 局部耗尽 → 收尾 → exhausted
       ├─ Planner 查进度 → 批准继续 W，保存原因
       └─ Attempt 2 / S2 → 恢复同一 Conversation → 完成
```

同 Run 保存的 HTTP 证据可供后续 Attempt 使用，保留现有来源校验，无需跨 Run 搬运或重复请求。

## 3. 分层预算与类型化准入

Run 保留模型总次数、工具总次数、整体时间、规划轮数、工作数及并发限制。Worker/Planner/收尾共同消耗这些授权，开始新 Attempt 不能重置已用量。

新增 Worker 每 Attempt 的模型次数、工具次数、运行时间和有界 settlement 配置；Planner 每轮也有局部额度和收尾。局部额度可重新获得，但每次调用必须同时满足局部和全局准入。

现有 SessionRunner 配置全局 gate 后会跳过本地计数比较，不能只加字段而保留该旁路。将 bool gate 改为携带作用域/原因的结构化结果，明确耗尽的是 Worker、Planner 还是整个 Run。

局部原因至少区分 worker_model_budget_exhausted、worker_tool_budget_exhausted、worker_timeout；全局保留 model_calls_exhausted、tool_calls_exhausted、timeout。局部耗尽只结束本轮，不能连带取消其他 Worker 或触发 Run Finalize。

Planner 一轮耗尽也不代表目标达成，未提交计划不应一律当系统故障；结合结构化结果、frontier 和目标判断。总预算不足以支持最低往返与必要收尾时不启动新 Attempt。

## 4. Settlement 是独立执行阶段

探索额度耗尽后，允许保存已经取得的观察/检查/进度，禁止新 HTTP 采集、发现或其他探索动作。收尾工具仍执行完整来源和执行上下文校验。

探索与收尾额度分别配置，均计入 Run 总量；ARTEX 有独立收尾轮数，我们在剩余总量内预留/申请，不绕过硬上限。Worker 收尾、Planner 收尾、Run 最终总结、数据库清理分开实现。

局部超时取消探索 context，在 Run context 仍有效时建立新的有界收尾 context。整体截止、用户停止和关机优先；全局模型/工具额度用完后，只能服务端保存已有结构化事实并用程序报告兜底，不能偷偷多调一次模型。数据库清理继续使用独立有界 context。

## 5. 工作状态、继续与依赖

| 情况 | Attempt / Session | WorkItem | Run |
| --- | --- | --- | --- |
| 满足完成条件 | completed | completed | 可继续 |
| 局部耗尽并收尾 | exhausted | exhausted | 保持运行，唤醒 Planner |
| 模型/网络故障 | failed，带具体原因 | failed/blocked，沿用统一语义 | 判断重试/换方向 |
| 用户停止 Run | stopped | 沿用停止语义 | stopped |
| 总预算耗尽 | 关闭活动子记录 | 保留未完成语义 | stopped / 部分完成 |

独立的继续服务执行 exhausted → pending → running，新建 Attempt N+1，保留 N 的状态、输出和证据。failed/blocked 可以明确故障重试，用户停止不自动复活；completed 不允许用“继续”重开，真正复测新建工作并注明理由。

事务、统一锁顺序、WorkItem 版本或 expected_attempt_id、唯一活动 Attempt 约束保证一个工作最多一轮执行。旧 Attempt 的迟到写入不能覆盖新 current_attempt_id。

依赖只由 completed 满足。exhausted 上游让下游等待，不误算已完成；上游恢复/完成后重新计算系统 dependency-blocked，不能把人工/实质阻塞一并打开。

## 6. 稳定会话与协议恢复

每个 Worker WorkItem 有稳定 Conversation，跨 Attempt 恢复原历史。执行 Session 记录本轮消息增量、用量、起止位置和恢复来源；历史消息保留原 Session/Attempt 所有权。

Planner 与 Worker 不同：对齐 ARTEX，每轮使用新 Session，输入当前态势、触发原因及跨轮共享待办，不要求 Resume 全部旧规划对话。增加 Run 级 PlannerTodo（状态、依赖、依据、版本）供规划轮次共享；若保存 PostgreSQL 实现跨进程恢复，明确这是对 ARTEX 进程内 TodoStore 的工程增强。稳定的 Planner 日志归档标识不等于每轮恢复完整聊天。共享待办不取代 WorkItem 的数据库领取条件。

现有 LoadSessionConversation 只加载一个 Session，需增加多 Attempt 历史加载，校验同 Run/WorkItem、模型协议及契约兼容性，按可靠序列组装。不要把历史再次 INSERT 为本轮消息，不按字符串粗暴去重。

Chat Completions 与 Responses 都要支持。Responses reasoning/function_call/function_call_output 等 NativePayload 原样保存并正确回放，不能只用自然语言摘要冒充原始工具历史。配置不兼容明确拒绝或要求显式重规划，不静默丢历史。

恢复对话与重放动作分开：

- 已有成功工具结果直接进入历史，不再执行。
- 同一助手消息的多工具调用若中途耗尽，给每个调用闭合协议结果；未执行明确标记未执行，不伪造成功，不在下一轮重放整个批次。
- 执行过但结果未落库标记未知/中断；有副作用的动作禁止自动重放。只读重试是新的、计费的调用。
- 数据库写工具通过事务性操作标识/幂等结果保护“提交成功但响应丢失”的窗口；复用真实已提交结果，不重复写观察，不让模型操作人工审核。

新 Attempt 以当前工作及继续指令启动。完成校验考虑同 WorkItem 的历史成果与当前目标：不能因本轮没有新观察就误判 missing_observation，也不能仅凭任意旧成果放行未完成目标。

保留原始 transcript，采用明确的长历史处理：压缩检查点记录消息边界，不破坏工具配对/NativePayload；至少有显式超限和可读进度回退，禁止无声截断。区分完整恢复与显式摘要回退。

## 7. Planner 续派和防空转

增加结构化 action/工具，例如 continue_work_item(work_item_id, expected_attempt_id, reason)，由 Planner 或人工接口调用。服务端校验状态、版本、范围、Run 准入和剩余预算；Worker 不能给自己续额。

Planner 先查 trace/output，再选择继续原工作、新建不同方向、故障重试、等待或完成目标。原因与依据持久化。ARTEX 的自动续派策略主要在提示词中；结构化继续操作是本工程的适配，并非 ARTEX 的原样 API。

配置每工作续派次数、连续无新增进度阈值和 Planner 轮次上限。进度依据持久化证据/实际状态变化，不能用重复总结、重复观察或 token 消耗冒充；不能换 key 绕过限制。达到阈值展示停滞原因。

Worker 结束通知调度器，唤醒 Planner；持久化状态配合通知合并，避免漏唤醒或重复认领。Run 完成依据目标、frontier、活动和可恢复工作，不能“没有 Worker 在跑就完成”。

## 8. 人工继续与整个 Run 恢复

活动 Run 内的人工继续/故障重试复用同一服务事务，幂等成功后通知已有 Engine，不启动第二个 Engine。

总预算耗尽或关机 interrupted 后需要整体恢复时，保持原 Run/WorkItem/Conversation，引入执行代次 execution epoch，不能只 UPDATE status；不再用新子 Run 代替这一功能。

每个 epoch 保存编号、起止时间、结束状态/原因、结果快照。首次为 1，恢复时：

1. 用户显式请求并提交幂等键；总预算耗尽才补充授权，interrupted 恢复不自动补回已消耗预算。completed、用户主动停止或未知失败不自动恢复。
2. 事务锁 Run，确认无活动子记录、旧 Engine 已撤销、同 Task 无其他活动 Run；建立 epoch N+1，才更新 Run 当前执行状态为 queued/running。
3. 原 execution_input 保留原始授权；新增额度进入不可变 budget_grants。有效总量为初始授权加追加授权，已用量不归零。时间追加记录批准时刻、秒数、新窗口和 deadline，不偷偷重置旧截止时间。
4. 准入、认领、模型/工具写入、收尾携带 epoch，旧 epoch 迟到写入必须拒绝。只检查 Run status=running 不足够。
5. 若更新 Run.final_output 当前投影，先保留旧 epoch 的报告、状态和原因；旧 Attempt、检查和人工审核不改写。
6. Manager 注册和释放也校验 epoch，旧 goroutine 退出不能移除新 Engine。重启撤销旧执行资格，关闭悬挂 Attempt，再进入明确待恢复状态，不自动复活用户停止。

追加授权只有用户可操作，Planner 无权自动创建。幂等识别先于活动状态冲突；同键同内容不重复恢复，不同内容 409；0/负数/缺失/超限/溢出拒绝。启动失败有持久化结果，不能永久 queued。无需本阶段实现多实例调度，但单进程重启和旧代次隔离必须可靠。

epoch、授权账本和全局次数硬上限是适配本工程审计设计，不是 ARTEX 的原样数据结构。要准确说明有意差异。

## 9. 页面和报告

WorkItem 展示稳定目标、Attempt 历史、各轮额度/用量/原因、恢复来源、续派理由和新增进度。局部耗尽显示“本轮额度耗尽，等待规划”，不能显示整个 Run 失败。

“继续此工作”消耗已有总授权；“追加总预算并恢复”是另一个明确动作，表单需展示两者区别、资格和额度。冲突刷新后由用户重新判断，不静默覆盖。

报告分别显示局部耗尽、续派次数、真实总用量、每 epoch 结束结果及未完成工作。复用对话不增加虚假访问/检查覆盖；第九阶段审核完整保留。

## 10. 实施顺序：四部分均属阶段交付

| 子阶段 | 内容 | 核心证明 |
| --- | --- | --- |
| 10A | 分层预算、类型化原因、局部 settlement、依赖等待 | 局部耗尽不会结束仍有额度的 Run |
| 10B | Worker Conversation、多 Attempt 恢复、协议闭合、Planner 共享待办及续派 | 同一工作沿用真实历史继续完成，规划跨轮不丢待办 |
| 10C | 人工继续、CAS/唯一约束、通知/重启、页面报告 | 停止、重试、并发不交错写坏 |

## 11. 必须验收的边界

1. A 局部耗尽保存进度，B 不被取消，Run 继续，Planner 能读取 A 真实 trace 并作决定。
2. 同 WorkItem Attempt 2 恢复原历史，Attempt 1/S1 仍终态；已保存 HTTP 响应不再请求，后续检查来源仍正确。
3. 两种模型协议均正确恢复，Responses NativePayload、多工具配对、未执行/未知结果没有伪造或副作用重放。
   Planner 每轮新 Session，跨轮待办保留、依赖事实出现后再派下一步；重启恢复按本工程持久化策略验证，不冒称 ARTEX TodoStore 已天然跨进程持久化。
4. 探索、settlement、Planner、最终总结全计入总硬上限，多 Worker 并发不超额，耗尽作用域准确。
5. exhausted 不满足依赖，继续后系统阻塞正确解除，人工阻塞保留。
6. 并发继续最多创建一个活动 Attempt，编号唯一，旧 Attempt 不能迟到覆盖；completed 不误重开。
7. 无进展达到阈值停止空转，不用新 key 绕过；旧观察不能冒充本轮新进度。
8. 探索/收尾/续派/模型返回时用户停止均优先，所有子记录有界结束，清理不被取消 context 吃掉。
9. 故障/重启保留消息与证据，未完成工具状态明确；不重置用量，不自动恢复用户停止。
10. 总预算耗尽后用户批准新 epoch，在同 Run/WorkItem 推进；旧响应、Finalize 和 Manager 释放均无法影响新代次。
11. 追加授权、恢复幂等和单活动约束正确，启动/事务失败无半条账本，历轮报告与审核可追溯。
12. fixture 完整跑通采集部分进度 → 局部耗尽 → Planner 续派 → 恢复完成 → 检查 → 人工审核；另跑总预算耗尽 → 人工追加 → 恢复。不能手工改成功状态冒充 Engine 链路。

使用专项 fake provider、本地 fixture、独立 TEST_DATABASE_URL。测试会清表，不能连接开发库；不调用真实模型或靶场。执行相关 race/生命周期/预算/证据/审核回归、go vet、前端构建及浏览器验收，记录真实结果和未完成项。
