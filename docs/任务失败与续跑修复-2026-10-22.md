## 本轮处理

| 问题 | 修复 | 保留的边界 |
| --- | --- | --- |
| Planner 暂时不可用直接导致整个 Run failed | 对明确可重试的 429、5xx、传输及上游超时错误，有界恢复仍失败后以 `stopped/needs_input` 收尾；保存诊断及结果，并提示恢复方式 | 原始失败模型调用和 Session 仍保留；401、协议及持久化错误不伪装成成功，也不无限重试 |
| 已到 Worker 预留线仍持续领取方向 | Dispatcher 在额度不足时不再领取；通知 Planner 评估一次，保留有界的收尾和显式恢复路径 | 总额度、Planner/Main 预留、Worker 局部额度均不调大 |
| 预留额度判断与扣费分开，存在并发穿透 | 在 BudgetManager 同一锁内检查预留并递增用量；增加 `worker_budget_reserved` 原因区分预留保护与总额度耗尽 | 所有真实模型请求继续记账；已有受限收尾规则不变 |
| 无效 continue/retry 造成空转 | 服务层在变更方向状态之前检查已持久化用量、预留及显式预算追加；不足则返回 `run_budget_exhausted`，不排队 | 运行时准入仍负责最终并发校验；续跑仍是同 WorkItem 的新 Attempt，不清空历史 |
| 工作项上限反馈不够可执行 | submit_plan 返回结构化错误，含已用、拟新增及上限；告诉 Planner 不要换 key 绕限；成功时返回真实工作项记录 | 仍限制总方向数，不把同方向续跑伪装成新方向 |
| Worker 不知道资产 UUID 对应哪个 URL | 初次及恢复输入均加入服务端生成的当前方向资产映射；强化 get_endpoint 参数 schema 和可纠正错误提示 | UUID 及范围校验照常执行，不接受 URL 自动冒充资产 ID |
| continue_work 的 Attempt ID 容易混淆 | Planner 当前态势包含 current_attempt_id；schema 明确该字段可省略，只可填当前实际 UUID | 过期 Attempt 的冲突检查继续保留，不自动绕过 |
| 任务停止后无法在工作台先追加授权 | 统一控制入口允许用户给 stopped/failed/interrupted Run 结构化追加预算，再显式开启新 Epoch | 追加只写授权账本，不自动启动任务；模型角色仍无权加预算；completed 保持只读 |
| 页面只有状态，缺少恢复说明 | 工作台显示结束原因和保存的说明，区分待处理、预算耗尽和模型服务异常；新 Epoch 按钮明确为继续任务 | 不修改历史失败任务的原状态，不把未完成任务显示成成功 |

register_asset 的范围拒绝属于授权校验正常生效，本轮没有放开范围。提示词和 UUID 映射能减少参数错误，但不能保证模型从此不会填错参数。

## ARTEX 对照与工程差异

只读核实相邻 ARTEX 的 `server/engine.go:plannerLoop`：一次 Planner 出错时记录日志，循环仍可等后续事件或心跳。Worker 的执行状态区分正常完成、局部耗尽和受阻；`agent/worker.go` 按稳定意图保留对话并允许恢复。

本轮沿用“规划暂时出错不抹掉已有工作”的机制；工程适配是本项目已有总硬额度、有界请求重试、统一收尾和显式 Epoch 恢复。因此持续上游错误后先停止并请求处理，而不是无限消耗模型请求或自动创建新 Run。保留 PostgreSQL、授权账本、幂等和旧代次保护，不声称这是 ARTEX 原样错误策略。

## 用户如何继续旧任务

旧 Run 保留其原始 `failed/provider_error` 记录。等待模型服务恢复后，可在工作台追加确实需要的模型次数和秒数，再填写原因点击“继续任务（新 Epoch）”。原任务累计已用 70 次模型调用，总额度为 80，且有 Planner/Main 预留；开启新 Epoch 不会清零用量或重新计算一份免费预算。

追加秒数是对原时间授权的增加，不能假定填入的秒数全部从点击时开始计时。没有明确追加时，不自动借用预留额度或扩大授权。
