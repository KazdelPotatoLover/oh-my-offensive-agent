## 2. 目前缺少什么

## 3. 配置与部署

在 .env.example 添加占位符说明；真实配置只由用户写入本地 .env，不提交密钥。示意：

```dotenv
LLM_BASE_URL=https://your-gateway.example/v1
LLM_API_KEY=由用户在本地填写
LLM_MODEL=服务商实际提供的模型ID
```

现有适配器会在 LLM_BASE_URL 后追加 `/chat/completions`，所以这里填写协议根地址，不填写完整的 `/chat/completions` 地址。具体是否包含 `/v1` 以实际服务商为准。

在 Compose 的 backend.environment 添加三项变量映射，前端不接收密钥。保持配置缺失时给出明确错误，不静默退回 Mock；缺配置也不影响已有 Mock 模式启动。

修改后使用 `docker compose up -d --build backend` 更新后端。部署前确认没有需要保留的活动 Run，避免重建打断它们。不要打印 docker inspect 的完整环境或 docker compose config 的展开结果；验证只输出配置是否存在与脱敏的服务、模型信息。

界面中原有 OpenAI Real 选项使用的是兼容协议，可改成“Chat Completions 兼容 API”，避免让用户以为只能选择一个厂商。保留底层 provider 标识的兼容性。

## 4. 第一次真实调用：最小工具循环

先用现有固定样本完成一次小任务，目标是让模型选择并读取指定样本，再根据实际结果返回答案。选择真实 Provider、有限预算与非流式调用。

必须验证：

1. 请求发送到了配置的服务与模型，没有落入 Mock。
2. 模型实际返回 tool_calls；程序执行真实工具。
3. 工具结果带正确 tool_call_id 回交；模型继续回复。
4. 消息、模型调用、工具调用与最终输出持久化，刷新页面仍能查看。
5. 认证、模型名、协议错误明确显示，没有伪造成功或自动切换 Provider。

本次使用的端点与模型必须支持当前协议下的函数工具调用；普通文本聊天成功不足以证明工具循环兼容。先核实服务商对目标模型的支持，不根据接口名称推断所有模型都可用。

OpenAI 官方工具调用机制参考：[Function calling](https://developers.openai.com/api/docs/guides/function-calling)。本文不指定模型品牌、版本、价格，也不宣称第三方兼容端点已通过验证。

## 5. 第二次真实调用：小范围编排

第一项通过后，创建一个独立的真实模型联调任务，使用用户提供的靶场。

建议先限制：种子只有首页；精确 origin 为 `http://192.168.77.88:7780`；允许路径为 `/`、`/news`、`/about`；GET；最多 3 个页面；深度 1；1 个 Worker；HTTP 请求间隔至少 500 ms。使用显式白名单模式，不改变已有较大范围任务。

总预算先设模型请求最多 20 次、工具请求最多 30 次、规划轮次最多 5、工作数最多 6、总时间最多 180 秒。达到预算时明确保留部分成果和结束原因。预算用于控制调用次数与执行时长，不等于精确费用上限。

期望行为：真实 Planner 根据首页资产安排工作；真实 Worker 读取页面并提取实际链接；程序过滤到允许范围；后续 Planner 根据已发现资产继续派工；最终报告引用真实观察与证据。

通过后再逐步恢复到最多 20 个页面与 2 层深度，不直接把第一次真实调用扩大成全面测试。

## 6. 针对真实模型要收紧的接口契约

Mock 知道项目内部约定，真实模型只知道传给它的提示词和工具描述。本阶段一起完成以下必要修正，不另起新架构：

- submit_plan 明确列出支持的 work_type、每种类型必需输入、资产 ID 与来源 ID 的含义。
- 未知工作类型在提交计划时拒绝，返回可修正的结构化错误；不能把未知类型默认为读取样本。
- Planner 的提示词说明稳定 key、已处理资产、重复提交、依赖、范围、预算与结束条件；不硬编码靶场端点清单。
- Worker 的提示词说明应完成的工具步骤、来源 ID 如何取得、怎样区分观察和猜测。
- 对外部网页正文保持数据身份，不能把正文中的文字变成 system 指令或执行范围。
- 工具结果过长时，给模型格式有效的摘要和证据引用；不截坏唯一原始证据。
- Run 级总预算在每次真实模型与工具请求前实际检查和预留，覆盖 Planner 与 Worker。仅累计监控计数不构成硬限制。即使只有一个 Worker，也不能每个 Session 各拿一份完整 Run 额度。
- 先保持模型请求不自动重试；若后续加入重试，明确哪些失败窗口可重放，避免重复工具操作。

## 7. 联调记录与验收

先运行协议 HTTP stub、数据库回归与类型检查，再进行用户配置好的真实服务验证。真实服务未配置时，交付应标为“代码与配置准备完成、真实调用待验证”，不能声称真实模型联调通过。

每次真实验证记录 Run 链接、脱敏服务地址、实际模型 ID、协议、提示词与工具版本、模型请求数、工具请求数、耗时、实际返回用量和结束原因。模型未返回用量时显示未知；没有价格配置与依据时不估算账单。

区分三种验证：Mock + 真实工具、HTTP stub 协议测试、真实模型 + 真实工具。界面与报告都保留 Provider 身份，不用 Mock 的 Token 数代替真实消耗。

对已有 completed Run 中的失败子调用，检查最终报告能否显示失败、未提取页面和不完整结果。流程完成与所有子操作成功分别表达，不因为有一个可恢复工具错误就隐藏它，也不无条件判整次任务失败。
