# ARTEX 后续能力对照与优先级

日期：2026-10-22。对照相邻 ARTEX 本地源码与当前 oh-my-offensive-agent（`4e204f2` 加本地任务失败/续跑修复）。本次是静态源码审查和学习建议，没有修改业务代码、启动扫描、调用模型或更新服务。

## 1. 判断

现有项目已具备 Main、Planner、独立 Dispatcher、N Worker、稳定方向与多 Attempt、事实图、目标证明、可信 HTTP 捕获和统一控制。下一阶段应补齐这些核心机制在真实网站任务中的使用能力，不必重新增加一套编排框架。

对用户“检查自己的网站、形成加固建议”的用途，优先级是：先补当前接线缺口，再让 Worker 能按方法识别接口、复用已抓流量、使用授权身份核验问题，最后交付可复测的报告。浏览器用于补足动态站点；复杂知识压缩、跨任务继承和完整插件平台可后续推进。

以下“缺口”依据源码范围判断；模块已存在但尚未完成实际闭环的，不写成完全没有。

## 2. 先补的工程缺口

### 2.1 新 HTTP 工具与旧发现、覆盖统计尚未统一

本项目已经把 `http_request` 接入可信收据、观察与事实，但还有两处旧口径：

- `backend/internal/service/coverage.go:ListAssetCoverage` 的 visited 只判断成功的 `get_endpoint` 和 `read_sample`，没有计算 `http_request`。
- `backend/internal/tools/discovery.go:ExtractEndpointLinksTool.Execute` 明确只接受 `get_endpoint`，其他来源工具会被拒绝。

影响是：使用新工具访问的目标可能仍被显示成未访问，Planner 因而重复安排；新 HTTP 工具的正文也不能直接沿用链接提取入口。这里只确认静态缺口，不声称它已经解释某个历史任务的全部覆盖问题。

建议把“成功读取目标”的判断及正文读取建立在同一可信 exchange/receipt 适配层，供覆盖、发现、观察和验证复用。继续校验 Run、Epoch、真实调用绑定、资产关联、正文完整性及当前授权，不通过简单放行工具名绕过来源验证。

对应 ARTEX 的学习点是 `traffic/traffic.go` 的统一已抓流量查询，以及 Worker 先查已有流量的策略；不是宣称 ARTEX 使用了本项目的 receipt 表。

### 2.2 意图图概览的摘要字段不一致

`backend/internal/service/intent.go:linkPlannedIntent` 把目标写入 payload 的 `text`；`service/exploration.go:GraphOverview` 对意图却读 `summary`。这条写入路径的意图摘要可能为空。

建议统一读取规范，兼容已有 `text/summary`，并在概览中包含简短的上游来源和真实终态原因。已有 work 列表和 trace 不必重建。

ARTEX `agent/planner.go`、`agent/tools.go:graphOverviewData` 会将运行中和近期结束的方向、状态、事实来源等组织成规划输入。值得学习的是态势信息的准确与紧凑。

### 2.3 工具级 panic 保护

ARTEX `agent/assembly.go:AugmentTools` 为最终工具统一包裹 `guardPanic`，避免单个工具 panic 终止整个服务。

本项目 `agent/session_runner.go` 和 `controlplane/main.go` 的工具执行路径直接调用 Execute，在检查到的工具层没有同等统一保护。这是静态风险，尚未以故障注入复现，也不是已确认的上次失败原因。

建议在共同执行边界保护工具的 Validate/Execute，将内部异常记为真实工具失败；原始堆栈仅放受控服务日志，模型只获得脱敏错误。覆盖 Main、Planner 和 Worker，避免只保护其中一个角色。不要因此把数据库写入失败吞成成功。

## 3. 最值得补的实际任务能力

| 顺序 | 能力 | ARTEX 实际参考 | 本项目现状 | 建议的最小增量 |
| --- | --- | --- | --- | --- |
| 1 | 已抓流量检索和证据复用 | `traffic/traffic.go:Tools` 的 traffic_search/get/blob；`agent/worker.go` 的流量提示 | 有收据、捕获正文、通用产物读取和 Worker trace 查询；缺少等价的、面向 HTTP exchange 的检索工具 | 按当前 Run、授权 origin、URL、方法、状态筛选，返回小索引；按 ID 取报文及分段正文 |
| 2 | 可执行的方法与技能 | `agent/assembly.go`、`server/assembly.go`、`agent/deferred.go`，按角色绑定技能/MCP，并在恢复时重建解锁状态 | 有能力 profile 和工具注册；尚无同等技能加载、脚本材料和依赖发现机制 | 先提供两个版本化本地技能：接口侦察、问题验证；技能声明需要哪些工具/镜像，加载不扩大权限 |
| 3 | API 与动态页面发现 | `skills/api-recon/`、`skills/playwright-cli/`；`agent/tools_insert.go` 的 endpoint method/params | 主要是 HTML 链接发现；有 http_request，但没有运行时浏览器工具和结构化 API/参数发现闭环 | 先静态 HTML/JS 提取候选接口，再接一个受控浏览器适配器；把页面、路由、方法、参数和请求样本分别记录 |
| 4 | 授权身份与问题核验闭环 | ARTEX 的浏览器技能、通用工具和独立 retester；不把它描述成自动完成所有鉴权业务的专用系统 | netcap 已支持服务端凭据、登录会话、会话隔离、显式共享和脱敏，缺少完善的用户配置及业务流程验证 | 让用户在本地配置账户 A/B 的凭据引用和身份说明，Worker 通过引用使用；验证同一资源在不同身份下的可见性并保存对照 |
| 5 | 面向修复的报告与复测 | `agent/promptcatalog.go:ReporterDefaultPrompt`、`agent/finding_workflow.go`、`agent/retester.go`、`server/scheduler.go` 的触发机制 | 已有 Finding、人工审核、修复建议、HTTP 条件验证及独立 RetestExecutor；没有同等完整的报告交付链 | 复用现有验证器核验候选，再由只读报告步骤汇总已存证据、影响、修复建议及复测结果，按 Finding 保存 |

不必等完整 MCP 管理页面、脚本市场或许多新角色实现后才做上述能力。可以先复用现有 profile、WorkItem、产物、预算池和事件机制，交付一条实际可用的任务链。

### 3.1 技能与工具的关系

工具解决“怎样发请求、运行脚本、读取材料”；技能解决“这个任务怎样推进、缺什么证据、何时结束”。仅把说明塞进提示词不能使缺失的工具可执行。

当前执行镜像主要是 Python/curl，命令 allowlist 也只允许 python/python3/curl。ARTEX 的浏览器/API 侦察材料涉及浏览器或 Node/Puppeteer 等依赖。不能复制一份 SKILL.md 就宣布浏览器能力完成；需要对应镜像、执行入口、网络授权、超时及产物接线。

技能中应明确产物和停止条件。例如接口侦察产出 method/path/参数位置/样本来源/置信度；验证产出基线、测试观察及结论依据。技能步骤由 Worker 自主选择和组合，不把所有网站固定成一条扫描流水线。

### 3.2 ARTEX API Recon 中容易误解的一点

该仓库的 `skills/api-recon/SKILL.md` 明确将自身限定为 API/参数面侦察。其动态模式允许用 mock/stub 撑开前端壳层，记录前端会发出的请求；它不等于拿到了真实登录态，也不证明后端存在越权漏洞。

借鉴时必须将静态候选、浏览器模拟流量和真实服务端响应分开。模拟响应不能产生真实目标的 verified fact、漏洞验证或目标证明。是否在授权身份下实际请求后端，是另一条需要真实证据的步骤。

### 3.3 报告不能替代验证

ARTEX reporter 的主要职责是读取已登记 Finding 的证据和执行过程，生成并保存 Markdown；不能把有 reporter 解释成存在一个自动、可靠的漏洞裁判。流量绑定也受设置和工具绑定控制，不保证所有部署默认开启。

本项目当前 `ReportFinding` 在经验来源下校验真实请求来源，验证条件可选；因此“来源可信”与“漏洞命题已被充分证明”仍须区分。下一步应强化实际问题的基线、测试响应、身份与前置条件，而不是继续增加 verified 标签。

现有 RetestExecutor 对不安全重放、认证或其他证据不足场景会返回 inconclusive。扩展复杂复测时应提供显式的身份和验证上下文，不删除这类限制，也不能把一次 403/404 当作加固成功。

## 4. 后续学习项

### 4.1 更好的态势和长任务记忆

ARTEX `agent/compaction.go`、`agent/coldgraph.go` 会识别与活跃方向有关的热节点，把冷事实/已结束意图组织成可展开摘要；`agent/tools_digest.go` 提供展开入口。模型压缩并非每次规划都调用，存在阈值、并发和版本处理。

本项目已有协议块安全的对话压缩及 checkpoint，但主要保存截取摘要；Planner 仍拼入较多完整观察。事实列表也主要是 limit 查询，缺少 ARTEX 那样完整的关键词/游标检索。可以先做有界态势摘要、事实检索和证据按需读取，再考虑冷图压缩，不急于另建复杂摘要系统。

### 4.2 跨任务知识复用

ARTEX `db/exploration_sources.go` 支持读取直接关联任务的事实、详情和过程，并标记继承来源。本项目当前主要以 Run 隔离共享知识。

这有助于同一站点后续复查，但优先级低于把一次任务做完整。以后加入时应由用户明确关联来源，旧任务知识作为线索，当前授权和证据仍需重新核对；不能把跨任务材料直接当本轮实测。

### 4.3 自定义工具、MCP 和模型配置

ARTEX 有按角色绑定、描述覆盖、外部工具与技能发现等能力。可逐步借鉴，但不要先建设一整个插件平台。先证明一个新增工具可被授权、装配、执行、追溯和恢复，再扩展通用管理。

保留本工程服务端工具注册、隔离 Broker、统一模型准入与额度记账。没有必要复制 ARTEX 的宿主机通用 Bash 环境来替代现有隔离边界。

## 5. 建议的下一轮交付

顺序可以压缩为三个小阶段：

1. **补齐共同证据接口**：解决 HTTP 覆盖/发现口径、意图摘要和工具异常保护；加入流量查询，Worker 能直接复用同伴已抓材料。
2. **交付一个网站检查流程**：两个本地技能、结构化 API 侦察、授权身份配置，必要时加入受控浏览器。让不同 Worker 分别收集入口、分析身份边界、核验线索，交换真实 Fact/Artifact/Exchange ID。
3. **形成修复闭环**：候选问题核验、基于证据的 Markdown 交付、用户加固后针对同一问题复测。模型与网络故障如实保留为受阻或 inconclusive。

有代表性的受控网站任务跑通即可作为这一轮的交付证据：入口发现 → 两个方向共享材料 → 问题核验 → 报告 → 修复后复测。无需额外引入完整发布演练或 20 轮压力测试作为前置门槛。

本次只完成对照与建议，上述增量尚未实施。此前任务失败/续跑修复仍留在工作区，不与此次审查混入同一已完成声明。
