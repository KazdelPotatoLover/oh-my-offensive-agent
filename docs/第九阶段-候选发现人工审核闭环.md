# 第九阶段：候选发现人工审核闭环

> 架构定位修订：本阶段是候选发现处置，不等于 ARTEX 的全部人在环路。执行纠偏、目标调整及独立复测另有职责，不修改本阶段“确认配置不等于漏洞验证”的含义。见 [架构对齐审查](ARTEX架构对齐审查与路线修订.md)。下文保留原阶段设计。

本文是待实施设计，不表示功能已经完成。基线为 `c7181c6`，编写日期为 2026-10-21。

## 1. 这一阶段要解决什么

第八阶段已经能从保存的 HTTP 响应计算规则结果，并生成 `pending_review` 候选发现。现在需要让人查看证据、作出判断、留下理由，随后在页面和报告中看到一致的结论。

本阶段完成后，一次完整使用流程是：

1. 打开 Run，展开某条检查结果及候选发现。
2. 查看规则名称、版本、有限的判断范围、响应证据和修复建议。
3. 选择确认、误报或忽略，提交审核说明。
4. 页面显示最新状态、版本、审核人、时间及历史；刷新后仍然存在。
5. 查看报告，按最新审核状态分类统计；原执行报告仍可追溯。

`confirmed` 表示人工确认这条配置发现成立，例如缺少某个响应头。它不表示完成了漏洞利用验证，也不表示站点存在可利用漏洞。

## 2. 架构：执行链和审核链分开

执行链：`HTTP 工具证据 → CheckResult → pending_review Finding`。

审核链：`人工请求 → 审核服务事务 → Finding 当前状态 + 追加审核历史 → 页面与当前报告视图`。

| 对象 | 表达的事实 | 本阶段允许的变动 |
| --- | --- | --- |
| 工具响应、观察、CheckResult | 当时采集到什么、哪版规则如何计算 | 不修改 |
| Finding 来源、内容、风险等级、证据引用 | 由哪条检查产生什么候选发现 | 不修改 |
| Finding 审核状态及版本 | 人当前如何判断该候选发现 | 通过审核服务更新 |
| 审核历史 | 谁在何时把什么状态改为什么、理由是什么 | 只追加 |
| Run 终态、结束原因、执行总结 | 当次执行如何结束 | 不因审核变化 |

Engine/Worker 负责执行，不参与人工审核。审核不消耗模型或工具预算，不创建 Attempt/Session，也不重启 Run。终态 Run 可以继续审核；运行中的 Run 已产生的 Finding 也可以审核。

避免把审核接口复用成 `RecordCheckResults`：后者需要活动执行上下文，人工审核的生命周期不同。

## 3. 状态与转换

沿用已有状态，不新增同义状态：

| 状态 | 页面含义 | 理由要求 |
| --- | --- | --- |
| pending_review | 待审核 | 初始生成时不要求；重新打开时必填 |
| confirmed | 已确认配置问题 | 必填，说明依据 |
| false_positive | 误报 | 必填，说明证据或适用范围为何不足 |
| ignored | 忽略 | 必填，说明为何暂不处理，不等于误报 |

允许待审核进入任一审核结论；允许已审核结论之间修正，也允许重新打开为待审核。不同状态之间的每次转换都必须带理由并追加历史。禁止同状态更新，重复请求按幂等规则返回原结果。

本阶段不编辑严重等级、规则结果或发现描述，不删除候选发现，不批量审核。

## 4. 数据设计

在 Finding 上增加 `review_version`（非空整数，初始 0）和必要的最后审核摘要字段。摘要与历史在同一事务中更新；字段采用项目既有命名约定。

新增 `finding_reviews`，至少包含：

- `id`、`finding_id`、`run_id`。
- `from_status`、`to_status`、`from_version`、`to_version`。
- `reviewer`、`comment`、服务端生成的 `created_at`。
- `request_id`：客户端生成的 UUID，重试时复用；按 Finding 和 request_id 唯一。

历史记录与 Finding 建立外键，按 Finding 和版本建立唯一约束。版本是历史顺序的依据，不仅依赖时间戳。历史不要级联删除；沿用项目现有删除规则并确保不会静默抹除审计。

当前若没有登录体系，使用界面显式填写的审核人名称，服务端校验非空和长度；文档说明这是用户自报名称，不能作为身份认证。已有认证则使用服务端身份，禁止客户端冒充。无需为本阶段引入账号系统。

迁移只补字段和新表：历史 Finding 保留原状态、版本 0，不伪造审核人或审核历史；已有非待审核数据若无来源，显示“无历史审核记录”。迁移回滚遇到实际审核数据应明确拒绝，避免静默丢失审计。

## 5. 接口与事务

建议沿用现有 `/api/runs/{runID}/findings` 作用域增加：

- `POST /api/runs/{runID}/findings/{findingID}/reviews`：提交转换。
- `GET /api/runs/{runID}/findings/{findingID}/reviews`：读取按版本排序的审核历史。
- 现有 Finding 列表返回当前状态、review_version 及最后审核摘要。

提交体包含 `status`、`comment`、`expected_version`、`request_id`；无认证时另含 `reviewer`。版本 0 必须合法，缺失版本必须报错，不能被默认成 0。正文大小与字段长度设置合理上限。

一次提交使用一个事务：

1. 校验参数，确认 Finding 属于路径中的 Run；错误作用域返回 404。
2. 锁定该 Finding 行。在版本检查前查询 request_id：相同请求内容重试返回原审核记录，不再次写入；同 request_id 不同内容返回 409。比较规范化后的业务请求内容，不受后来状态变化影响。
3. 比较 expected_version；过期返回 409 及当前版本/状态，禁止悄悄覆盖。校验目标状态和允许的转换。
4. 插入历史，将 Finding 状态、版本和最后审核摘要一起更新。
5. 提交后返回对应审核记录和当前 Finding。任一步失败整体回滚。

非法输入返回 400；未知资源返回 404；版本、幂等键和同状态转换冲突返回 409；数据库异常返回 500。错误结构沿用项目习惯。

不对终态 Run 调用执行状态更新函数。若复用 Run 事件展示审核动作，先核实终态是否允许追加事件，并把事件放进同一事务；审核历史始终是事实来源。本阶段可先通过主动刷新展示历史，无需改造 SSE。

重复检查仍按第八阶段规则去重，复用已有 Finding 时必须保留它的审核状态、版本和历史，不能重置为待审核。

## 6. 报告如何更新

现有 `orchestration/summary.go` 把 Finding 统一列在 Pending Review 下；这在加入审核后会误导，需要同步改造。

保留 Run 结束时保存的执行总结。新增独立的当前审核报告读取接口，例如 `GET /api/runs/{runID}/finding-report`：直接从数据库读取状态分类和发现列表，返回生成时间，页面标为“当前审核情况”。它不调用模型，也不覆盖原总结。

报告应在一致的数据库快照内形成统计和列表，可用单次查询返回全部 Finding 后在内存分类，避免统计与列表分别查询产生偏差。至少包含四种状态的数量、发现 ID、配置问题说明、规则/证据引用、最新审核版本和摘要。

第八阶段原有执行总结中的相关段落改为“执行结束时的发现快照”，明确时间与状态，不再把所有条目写死为待审核。原历史报告正文不做批量改写；展示时标注它是历史快照，并提供当前审核视图。

审核后的页面、Finding 列表和当前审核报告必须一致；误报和忽略项仍可追溯，不混入“已确认配置问题”数量。

## 7. 前端交互

在已有 `CheckResultsPanel.tsx` 上扩展，不另起一套工作台：

- 展示每条 Finding 当前状态、最新审核摘要和审核历史。
- 提供确认、误报、忽略、重新打开/修正入口；说明输入必填。
- 明示“确认配置问题不代表已验证漏洞”；忽略说明不等于误报。
- 提交期间禁用按钮；一次用户动作生成一个 request_id，网络重试复用它。
- 成功后重新读取 Finding、历史和当前审核报告，包括终态 Run 页面。
- 409 时刷新并提示已有更新，由用户重新判断；禁止自动覆盖或用新版本静默重试。
- 失败保留输入；审核人可在本地记住，但应明确其为自报名称。

## 9. 必须通过的验收

1. 本地 fixture 产生候选发现；确认后刷新仍显示正确状态、理由、审核人和历史，原 CheckResult/证据不变。
2. 误报、忽略、修正和重新打开均记录版本连续的历史；空理由、非法状态、缺失版本和错误资源作用域被拒绝。
3. 两个请求使用同一 expected_version 并发修改，仅一个成功，另一个 409；不存在历史与当前状态分离。
4. 同 request_id 同内容重试只产生一条历史；不同内容冲突。即使之后发生新审核，旧请求重试也不再执行转换。
5. 制造事务失败，Finding 与历史均不发生部分写入。
6. Run 在 completed、failed、stopped 等已有终态时均可审核；终态、finish_reason、会话、工作项和预算不改变。运行中的 Finding 也可审核。
7. 重新执行相同检查复用已有结果时，保留已审核 Finding，历史和版本不变。
8. 当前审核报告四类计数与列表一致；审核后及时刷新，原执行总结保留快照语义。
9. 原有检查、预算耗尽和 Run 收尾回归通过；模型无法通过工具修改人工审核状态。
10. 迁移在独立数据库验证，旧数据无伪造历史，降级不会静默丢失审核数据；前端构建通过，并记录浏览器交互验收结果。

集成测试只使用专门创建的 `TEST_DATABASE_URL`，测试会清表，不得指向开发数据库。使用 fake provider 和本地 fixture；不访问真实模型或靶场。默认不推送、不部署、不修改历史 Run。

## 10. 本阶段边界

自动续租、浏览器检查、主动漏洞利用、跨 Run 发现合并、账号权限系统、批量审核和严重等级人工调整继续延后。先把一条候选发现的证据、判断、历史和报告做完整。
