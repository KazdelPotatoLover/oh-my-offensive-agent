## 根因交给 owner

- Agent 1：`backend/internal/handler/run.go` 的 `startRunExecutor` 在发现模式把 `budget.MaxParallelWorkers` 写成 1。snapshot 和 effective 仍保留请求的 N。非发现 N=4 能出现 4 个重叠 worker。Planner 与 Dispatcher 共用一个循环，worker 被 barrier 卡住时 follow-up 模型调用不开始，在途 planner 调用期间只领到 2 个方向。A 未退出时，事实唤醒没有派出 B。`backend/internal/service/run.go` 创建路径复制了若干预算字段，没有复制 `worker_max_model_calls`；默认值 5 被写入 snapshot，worker 再加一次 settlement 后打到 6 次。
- Agent 2：一次 429 结束 planner 轮次，没有后续 5xx 再恢复到被接受的计划。N=4 时模型请求峰值是 4，没有共享 in-flight 上限 2。请同时通知 Agent 0：ModelCapacity 是读模型。
- Agent 3：HTTPS 种子被 `only http scheme is permitted for seed URL` 拒绝。身份别名和 TLS 请求没有发生。finish 复测要求结构化 `source_tool_call_id`，withdraw 路由不存在。A10 的峰值 1 先由 Agent 1 的发现模式串行造成。
- Agent 4：`run_command` 不在工具表，`execution_jobs` 关系不存在，没有按 run 标签观察到容器。
- Agent 5：planner 工具列表没有 `steer_work` / `kill_work`。`/main/messages`、`/commands`、`/workbench` 返回 404。生产 `backend/cmd/server/main.go` 当前也没有这三条路由。
- Agent 6：浏览器流未跑。独立 spec 已放在 `frontend/tests/ma-acceptance/`，没有改共享 Playwright 配置。
- Agent 0：路由挂载、Compose 端口和最终发布门禁。清单见 `证据/ma7/给Agent0的补丁清单.md`。
