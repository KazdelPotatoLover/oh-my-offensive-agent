## 谁来决定继续

当前模式已经允许 Planner 根据目标、事实、尚未验证的假设及已有成果，自主决定增派、继续同一方向、等待 Worker 或建议收尾。Worker 池大小只影响同时执行的数量，不限制累计能产生多少方向。

Agent 不需要事先决定“本任务最多规划多少轮”；让它在每轮根据进展判断是否继续更符合现有探索机制。但用户显式设置的硬上限、工具权限、授权范围和停止动作仍由程序执行，Agent 不能自行提高或绕过。

如果表现为“只规划了几个方向就结束”，应检查实际 `suggest_completion` 参数、目标证明、阻塞原因及收尾分支，不能仅凭方向数量归因于额度不足。本轮没有凭空提高已经不限的数字，也没有擅自解除网络策略。

## ARTEX 参照与本工程边界

- ARTEX `agent/planner.go` 将 `p.maxTurns` 传给 SDK，0 表示不限；单会话轮数可配置。
- Planner 没有自身墙钟额度，有任务 deadline 时被剩余任务时间夹逼。
- 每轮新 Session，读取当前态势并共享 TodoStore；本轮结束不等于整个探索结束。
- 显式单轮额度命中后的 settlement 由 ARTEX 使用的 agent-core SDK 处理。

本工程目前 `plannerCallGate` 执行 Run 的共享模型/工具准入，规划总轮数由 Engine 检查。`agents.planner.max_turns/run_timeout_seconds/settlement_max_turns` 的正数配置没有像 Worker 一样完整接入 Planner 局部 gate；因此不能宣称非零 Planner 单会话配置已经完整生效。默认 0 的自主探索不受这个缺口影响，也不需要为了本次核对新增一套局部额度机制。

相关入口：`backend/internal/model/execution_policy.go`、`config/exploration.go`、`orchestration/runtime_bind.go`、`orchestration/engine.go`、`orchestration/prompts.go`。
