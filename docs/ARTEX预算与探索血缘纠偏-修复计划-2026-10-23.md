## 4. 目标执行合同：版本明确，额度可选

### 4.1 新任务默认策略

| 项目 | 本轮目标 |
| --- | --- |
| Worker 数 | 默认 3，继承全局设置；有效上限仍保留本工程 1–8 |
| 任务总时长 | 默认无期限；用户可以在高级设置指定分钟 |
| Planner/Worker 模型、工具总次数 | 默认不启用业务硬上限；继续真实计数；专家/API 可显式启用 |
| Planner 总轮数、WorkItem 总数 | 默认不启用任意次数封顶；保留并发限制、方向去重与正常停止判断 |
| Worker 单轮 | 默认 MaxTurns=0、单轮探索时长 1200 秒；可继承全局 Agent 配置 |
| Worker 工具次数 | 默认不单独切断；显式旧配额/专家限制仍兼容 |
| Planner 单轮 | MaxTurns=0、自身时长不限；有任务期限时服从任务期限 |
| Main 对话 | 不再默认受整个 Run 累计 8 次限制；使用独立的单次交互配置和取消控制 |
| 局部收尾 | 独立配置，默认最多 10 轮，允许写回已有成果；探索阶段额度耗尽不挤掉收尾 |
| 外部请求保护 | 模型/工具单次超时、共享模型并发、网络间隔、隔离和输出上限继续生效 |

“无总次数上限”不等于取消请求超时或取消按钮，也不等于保证无限自动续派；由目标、证据、正常完成、受阻和用户控制共同驱动任务。

### 4.2 版本化与唯一权威配置

建议新增 `execution_input.execution_policy`，例如：

```json
{
  "schema_version": "agent_limits.v1",
  "task_timeout_seconds": 0,
  "agents": {
    "worker": {"max_turns": 0, "run_timeout_seconds": 1200, "settlement_max_turns": 10},
    "planner": {"max_turns": 0, "run_timeout_seconds": 0, "settlement_max_turns": 10},
    "mainagent": {"max_turns": 0, "run_timeout_seconds": 0, "settlement_max_turns": 10}
  },
  "hard_limits": {
    "model_calls": 0,
    "tool_calls": 0,
    "planner_rounds": 0,
    "work_items": 0
  }
}
```

字段名可以按现有工程适配，但以下合同必须满足：

1. **只有带新版本的策略才采用新语义**。没有新版本的旧 Run，完整沿用已有 BudgetConfig 与缺省规则；不能把旧 Run 中的 0/缺字段解释为无限。
2. 新策略内 0 明确表示该维度不设上限；覆盖请求用可选字段/指针区分“省略=继承”和“显式 0=不限”。负数非法；不得用 999999/MaxInt 伪装不限。
3. 解析后的策略在创建 Run 时完整冻结；执行、重启、Epoch、Main、前端读取同一个策略。保留兼容 budget 字段时只能作为明确的兼容投影，不能形成两套相反的权威配置。
4. 优先级：内置默认 → 全局 Agent/策略配置 → Task 显式配置 → 本次请求。已有 Task 中明确填写的正数旧额度仍映射为显式兼容限制；新建 Run 不得悄悄丢弃它们。
5. `worker_max_model_calls` 与 MaxTurns 不是可直接互换的同义字段。保留旧显式模型/工具次数限制的兼容入口，不能把旧 20 次调用简单改名成 20 轮。
6. 策略解析集中实现，禁止在每个入口自行填默认值。环境变量沿用/扩展现有全局入口或提供一个新入口均可，但旧 `OMA_EXPLORATION_BUDGET` 正数配置需要兼容，不要求普通用户重新填写。
7. 全局默认变化不修改已有 Run；幂等创建重试返回原策略。已有有界 Run 需要变更时走现有显式授权与恢复流程，不自动迁移成无界。

实现要求：

- 用显式 HasLimit/Enabled/可选上限表达无限；统一剩余量结果，审查所有 `<=0`、`>=limit`、`time.After` 和 timer 调用者。
- 无总 deadline 时不启动 0 秒定时器、不立刻取消，也不通过负数剩余时间触发收尾。

- MaxTurns 的一轮应是一次逻辑模型响应及其整批工具往返；同一轮多个工具不各算一轮。上游重试实际请求继续记账，但不能伪装成新探索轮次。
- Worker 局部轮数/时长触顶 → settlement → WorkItem/Attempt 正确 exhausted → Planner 事件唤醒。不得全任务 failed，也不得无条件自动充值/重开旧 Attempt。
- 独立收尾默认 10 轮；允许把已得结果落库，继续禁止新的探索工具。收尾自身也要有终止条件；用户停止、Epoch 失效和范围保护始终优先。
- Main 和 Planner 同样能结束单轮；Main 不因已经聊过 8 次而永久不能交互。
- 保留单次模型/工具超时、共享上游并发、原子计数和原有 provenance。不要为了对齐而把所有保护删掉。
- 去掉固定次数封顶后检查空规划轮的退避/等待：没有变化时不得紧循环反复调用模型。沿用当前事件合并和心跳，不新增重型主动监督系统。
- 专家显式配置硬上限时继续原子执行；其覆盖哪些角色要明确。当前 Main 独立记账，不得把 Planner/Worker 的上限宣传成所有角色的费用总封顶。本轮不要求重造统一计费系统。

## 6. 阶段 B：真实任务起点与产出链

### B1. 一个 Run 一个持久化起点

推荐与 ARTEX 一致：`kind=fact,state=origin`。内容来自 Run 的不可变目标/范围快照，来源注明 user/run_snapshot，不读取当前可编辑 Task 来覆盖历史。

- 新 Run 在创建事务中写入起点，再创建初始用户目标及其 spawns 边。
- 唯一约束或等效原子保证防止重复起点；先处理旧数据再建约束。并发 SetGoals/submit_plan 不得各插一个。
- 起点不是 HTTP 观察、已验证漏洞或 goal 证明；禁止将它升级 verified 或拿它证明目标完成。
- 节点可锚定原有种子资产，但不是跨范围授权。

建议抽出复用的 origin 查询/确保存在及边写入 helper，在既有 Run 锁/事务顺序内使用，避免新加相反锁序。

### B2. 所有真正的写入口使用相同关系规则

| 写入口 | 必须保存的关系 |
| --- | --- |
| 初始用户 goal、`SetGoals` | origin --spawns--> goal |
| `linkPlannedIntent` / submit_plan 的 intent | 无显式知识来源时 origin --derived_from--> intent；有来源时每个真实来源 → intent |
| `AddIntent`、Main/控制面 add_intent、种子/legacy 适配入口 | 同样的来源规则，不能只修 Planner 的一个入口 |
| `RecordFact` | 保留实际执行 intent --yields--> fact，包括去重 fact 被多个方向引用的场景 |
| `ReportFinding` | 当前可信执行上下文中的 intent --yields--> finding 节点 |
| `ProveGoal` | 仅继续使用实际有效、版本匹配的 fact/finding --proves--> goal |

- Goal 不自动成为所有 Intent 的父节点。没有记录“目标 A 分解出目标 B”时，不补出假的目标树。
- 来源要支持 fact/finding 的探索节点 ID，并校验同 Run、种类和未撤回状态；必要时给 source_fact_ids 保留兼容别名并增加明确 parent/source node 字段。
- 自动选择任务起点是明确的“无显式来源”规则，不是选择第一个普通事实。填写非法来源必须报错，不能吞错后回落起点。
- Worker→Finding 使用服务端可信 WorkItem/Attempt/Session 上下文建立关联；不让模型任填 WorkItem UUID 冒领归属。单独依赖 SourceToolCallID 可能把复用证据的另一个 Worker 当成报告者，必须区分“报告执行者”和“证据产生者”。
- 当前无执行方向的 Planner/Main 人工发现可以保持未归属，或保存明确的非 Worker 来源；禁止硬连第一个 Worker。
- 节点与边尽量在同一事务提交；错误必须返回，不能静默丢边。保留 `(run_id,src,dst,rel)` 去重，不按 src/dst 粗暴吞掉不同语义的关系。
- 原节点 ID、WorkItem/Finding ID 映射保持稳定；多个 Attempt 仍对应同一个 intent 节点。

### B3. 历史图的幂等回填

提供迁移或明确的修复命令，使已有任务也能看到任务起点；不要只修新任务，要求用户重建 Run 才有线。

允许回填：

1. 从已有 Run 快照恢复一个缺失的 origin，注明 historical_backfill 来源。
2. origin→既有 goal 的 spawns。
3. 对确实未填写知识来源的初始 intent，补 origin→intent 的 derived_from。
4. 有明确保存的 source_fact_ids/来源版本时恢复对应的真实派生边；有可靠执行归属时恢复实际产出边。

禁止回填：猜测某个普通 Fact 属于第一个 Worker；猜测目标父子关系；自动创建 proves；改原工作/审核状态；覆盖真实父边；把无法定位的来源冒充已知。

检查已有真实父边与原输入：来源字段存在但无效/已删除时保留诊断，不得用 root 兜底掩盖。回填可重复执行且不会产生重复节点/边，不改原 ID、原始证据、预算、Epoch 或终态。旧 begin 根需要明确复用或迁移规则，不能同时冒出两套“任务起点”。GET 图接口继续只读。

## 8. 最小验收矩阵

## 9. 交付与完成标准

建议按可审查边界形成提交：

1. `feat: version agent execution limits and preserve legacy budgets`
2. `fix: honor optional limits across scheduling settlement and recovery`
3. `fix: persist exploration origin and provenance with historical backfill`
4. `feat: surface inherited limits and real exploration lineage`

不为凑提交拆出不可运行的中间状态，也不要把其他 agent 的 MCP 修改混进本轮提交。

交付说明必须写明：ARTEX 对应机制、实际改动、有意差异、测试结果、历史图修复方法、当前运行服务是否更新。保留一个同 Run 的代表性证据链，展示初始连线→事实产出→后续派生；只截图一张静态图不足以证明写入机制。

最终不得仅用“构建成功”“预算改大了”“默认折叠了”“新任务有线了”宣布完成。预算语义、旧快照兼容、初始真实连线、历史回填和正常停止都成立，才算完成本轮。
