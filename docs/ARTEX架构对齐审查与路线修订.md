# ARTEX 架构对齐审查与路线修订

日期：2026-10-21。审查对象：前九阶段计划、当前实现 `74019b6`、尚未实施的第十阶段，以及相邻 ARTEX 本地源码。本文记录静态架构审查，未运行模型、靶场、数据库测试或部署。

> 本轮完整实施契约已整理为 [ARTEX 对齐改造总实施计划](ARTEX对齐改造-总实施计划.md)，使用 P0–P7 明确范围、顺序和验收。下文保留差异分析与原路线说明；执行顺序以总计划为准。

## 1. 结论

此前路线的基础设施有价值，但进入第五阶段以后逐渐围绕“页面采集 → 固定检查 → 候选发现 → 人工审核”推进，ARTEX 最核心的自主探索模型长期只停留在未来规划中。

初始学习手册已经写出双图、共享记忆、过程检索、重试和目标判断；问题主要是后续阶段持续延后这些内容，且没有明确补齐时间。不能把“有 Planner/Worker、能抓页面”当作已经接近 ARTEX 的自主执行架构。

用户现在明确以学习 ARTEX 为优先目标。后续需要复现机制，再解释有意保留的工程差异；不再默认以最小交付代替核心能力。

现有状态机、事务、工具留痕、资产身份、来源校验、Responses 适配、确定性检查和人工审核均可保留，不需要推倒重写。需要修正的是主线与部分职责模型。

## 2. 各阶段审查

这里使用实际已交付阶段编号；早期总手册的八课编号是原路线，不能直接视为当前完成进度。

| 阶段 | 与 ARTEX 的对应 | 判断与处理 |
| --- | --- | --- |
| 1：Task/Run/Event | 生命周期、后台执行、状态与控制 | 合理的工程基础。Task 定义与 Run 执行的拆分不同于 ARTEX 原结构，但不阻碍学习。保留。 |
| 2：单 Agent/工具循环 | SDK Session、模型工具往返、记录与取消 | 合理的教学拆分。手写运行时与 ARTEX 使用 Norma SDK 不同，应明确我们在学习 SDK 所承担的职责。保留。 |
| 3：Planner/Worker/Attempt | 意图领取与分角色执行 | 方向正确，但固定类型、单 Attempt、整批工作后再评估只能算过渡。局部预算原文有要求，实现没有完整落地，应作为设计债补齐。 |
| 4：资产与证据追溯 | 资产锚点、工具来源、探索血缘 | 打了基础；work_dependencies/source_observation_ids/asset_discoveries 分别表达依赖、来源和链接，尚不构成完整探索图。 |
| 5：本地 HTTP | 真实工具、请求/响应留痕 | fixture 是有效测试替身，但限定页面读取不能成为最终 Worker 能力上限。 |
| 6：链接发现 | 资产增量带动下一轮工作 | 已具动态派工雏形；目前核心仍是页面遍历，尚缺事实驱动的新方向、开放意图和目标证明。 |
| 7：真实模型/Responses/生命周期 | Provider、原始对话、取消与收尾 | 必要且可保留。协议历史可重载不等于跨 Attempt 恢复；总体失败策略与 ARTEX 的局部 blocked/exhausted 分流有差异。 |
| 8：确定性规则 | 作为执行器或专用工具可以共存 | 属于我们的配置审查扩展，不是 ARTEX 通用 finding 机制的复刻。不能把规则目录当自主探索的全部能力。 |
| 9：人工审核 | 有人在环路的处理界面 | 是有价值的治理能力，但主要覆盖发现处置；不等于 ARTEX 的主 Agent 对话、纠偏、暂停/重跑、目标调整与复测。 |
| 10：新修订执行模型 | 局部耗尽、会话恢复、续派 | 已修正主线。还需区分 Worker 历史恢复与 Planner 新会话/共享待办；epoch/grants 是适配，不是参考项目原样机制。 |

## 3. 最关键的差异

### A. 固定流水线与开放意图

本项目 `orchestration/prompts.go`、`tools/orchestration.go`、Engine 的 Worker 注册分支，将可执行工作限制在 inspect_http_endpoint / run_security_check / analyze_sample / aggregate_summary。一次 HTTP 工作读一页、登记链接后结束。

ARTEX `agent/tools.go` 的 add_intent 接收方向 summary、asset_ids、parent_ids、priority；`agent/worker.go` 中 Worker 对这个目标自主选择已提供的真实工具。意图来源可以是一个或多个事实，而不只是一个新 URL。

修订：把“工作意图”与“执行能力配置”分开。开放的是目标与推理路径，工具能力、权限、范围和预算仍由程序明确提供。保留现有专用工作类型作为执行适配器/回归场景，不能简单删除 enum 或无条件开放 Shell 来冒充自主性。

### B. 数据库有关系，不等于双图

本项目已有全局 assets、run_assets、工作资产/观察关联和页面链接；缺少结构化 Goal、带 observed/inferred 语义的 Fact、Hint、证明关系，以及通用事实 → 意图 → 新事实的血缘。

ARTEX `db/schema.sql`、`db/exploration.go` 定义任务内 exploration_nodes、exploration_edges、exploration_anchors；`db/assets.go` 管理全局类型化资产、归一化及去重。两图通过锚点连接，不只是 UI 上画两张图。

修订：用 PostgreSQL 实体与边表逐步补探索模型，无需先引入图数据库。现有 Observation 保留为原始输出的解释/摘录；Fact 是可复用知识陈述，保留置信类别、证据和失效状态；不能把所有观察直接升级为已确认事实。资产侧扩充类型、规范化身份和关系时保留范围授权校验。

### C. 工作做完与目标达成分开

目前 suggest_completion 主要排除 pending/running，再接受 complete/partial/blocked；没有结构化目标与证明关系。完成固定流程不等于证明用户目标。

ARTEX `agent/tools.go:1157` 的 prove_goal 关联 fact/finding 与 goal，逐项 met；全部目标满足可触发结束。注意源码仍暴露 goal_met 兼容入口，不能把提示词所说“唯一方式”当成服务端已完全禁止其他结束路径。证据存在也不代表程序能够自动证明任意自然语言目标。

修订：引入 Goal、明确验收条件、证据链接和 prove_goal 类动作；可程序核验的数量/覆盖条件由服务端核验，其余保留可审查理由。未达成但无可执行方向、预算耗尽和用户停止均有独立结论，不能误报成功。

### D. 批次循环与事件驱动规划

当前 Engine 主要是 dispatchWorkers → 工作批次结束/局部耗尽 → 下一规划轮；并非 ARTEX 常驻 plannerLoop + Worker 池、图变化/发现/心跳唤醒的完整模式。

ARTEX `server/engine.go:800` 使用合并通知、心跳和 guard 运行 Planner；Worker 写回 finding 可中途触发通知，而不是必须等全体结束。

修订：持久化有效变化、合并唤醒和必要心跳；Planner 可以等待依赖、返回本轮无新意图，不能必须每轮派工或建议整个 Run 结束。所有变动都调一次模型也不正确。第十阶段先补局部结束唤醒，探索图阶段再接事实/目标变更事件。

### E. 共享观察与过程级协作

已有 read_observations 和按 Session 留存工具记录，但 Worker 尚无 ARTEX 那样的本任务跨 work 过程检索；在页面能看到日志不等于 Agent 能按需使用它。

ARTEX `agent/tools.go` 提供 search_all_worker_traces、list_worker_traces、get_worker_trace，支持关键词、意图及步骤读取，让尚未写成正式 fact 的过程观察也能复用。

修订：增加结构化 trace 索引和分页/按步读取，Planner 与有权限 Worker 均可用。必须服务端校验 Run/来源范围，默认不拉全量 transcript；工具记录属于原执行者，查询不增加假覆盖。

### F. Worker 恢复与 Planner 记忆不同

本项目 Attempt/Session 已存在，但还没有稳定工作对话与完整恢复。ARTEX Worker 重跑同 intent 时 Resume 原 transcript。

另一方面 ARTEX Planner 每轮创建新 Session，输入当前图态势与触发原因，跨轮共享 TodoStore；稳定的 planner transcript 文件名主要提供累计记录，不能据此推断每轮 Resume 所有旧消息。`agent/planner.go:108` 的 TodoStore 是进程内 map，不能声称天然具备跨进程持久化。

修订：Worker 恢复原始对话；Planner 每轮新 Session + 当前态势 + 跨轮共享待办。我们可将 PlannerTodo 保存 PostgreSQL 以满足重启恢复，但必须标明这是工程增强，不是 ARTEX 已经如此实现。刚修订的第十阶段已同步纠正。

### G. 候选配置发现与实证 finding 不同

本项目 CheckResult 来自注册规则，只产生 pending_review；人工 confirmed 的定义是“配置问题成立”。这套语义准确，应该保留。

ARTEX `agent/worker.go:238` 区分 asset、fact 与 finding，要求 report_finding 有本次实际触发/可复现证据；怀疑或版本推断应记录 inferred fact，不直接上升为确认漏洞。

修订：不要把现有 confirmed 改名成漏洞已验证。将规则型配置候选、调查推测和实证发现通过来源类型/验证状态明确区分，未来单独设计验证与复测，旧审核历史不改写。规则检查是工具能力之一，不是全系统的唯一知识入口。

### H. 人工审核与人在环路控制不同

第九阶段只改变 Finding 处置状态。ARTEX `agent/mainagent.go` 还有任务对话、插入方向、steer_work、kill_work、目标和约束调整；README 描述独立 retester 会话保存复测历史。

修订：未来分别设计执行干预与独立复测，不要把“填写审核意见”宣称为全部人在环路。审核后的 Run 不必重新执行；对运行中的干预则必须使用执行控制协议。

### I. 执行工具与流量证据范围不同

我们只有少量 HTTP GET/样本工具。ARTEX 使用基础工具、Bash/WebFetch、MCP/技能等，并配有工作目录、输出溢出、压缩和记录代理。现有 get_endpoint 留痕只覆盖这一条工具路径，不代表能记录任意工具网络流量。

修订：在开放意图之后补可配置工具能力、工作空间、完整输出引用和实际流量记录。先证明不同执行器的来源追溯，再扩展能力；MCP 是扩展机制，不替代状态、目标或证据设计。先用本地 fixture 证明机制即可，不要求用真实攻击完成架构验收。

## 4. 应保留的工程差异

- PostgreSQL 事务、来源约束、计划原子提交、输入快照、幂等和迟到写入保护是基础保障。
- Run 总次数硬上限可以保留，但必须与 Worker 局部额度分层，不能把它误称为 ARTEX 原有预算模型。
- polling 与 SSE、分离前后端与内嵌部署、手写 runtime 与 Norma SDK 是实现选择，不决定是否掌握探索机制。
- 审核版本与审计保留是本工程选择。ARTEX 独立 findings 使用 task_id ON DELETE SET NULL；我们的“含审核历史禁止删除任务”不等于原样实现，但二者都有历史保留目的，不需要为了表面相似立即重写。
- 更严格的批量原子性与证据归属可以保留，不照搬 ARTEX 的部分成功行为。

## 5. 修订后的后续主线

| 顺序 | 要补的核心 | 可验证成果 |
| --- | --- | --- |
| 第十阶段 | 分层预算、Worker 恢复、Planner 新会话/共享待办、续派与控制 | 同工作多轮推进，不重复已完成动作，不把局部耗尽当整体结束 |
| 第十一阶段 | Goal/Fact/Hint/意图血缘、资产锚点、目标证明及有效事件 | 能回答“为什么派这一步、证据是什么、哪个目标已满足” |
| 第十二阶段 | 开放意图、能力配置、跨 work trace 检索、工作空间 | 相同工具可按不同目标组合，Worker 能复用他人真实过程 |
| 后续扩展 | 人工对话/纠偏、独立复测、工具扩展、代理留痕与知识压缩 | 人能控制探索方向，验证历史、过程证据可追溯 |

第十阶段已经涉及 trace/output 基础与 PlannerTodo，不需要为了编号等到十二阶段才有最初的过程读取。十二阶段把它扩展为完整的过程协作和能力模型。

epoch/追加账本属于十阶段的审计适配；分批实现时先验收与 ARTEX 对应的预算、恢复和规划，再实现总授权恢复，不让账本复杂度遮住双图与自主探索的主线。本文十一/十二阶段是路线修订，尚不是可直接据此编码的详细契约；届时先读源码再写完整计划。
